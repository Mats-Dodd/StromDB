# strom-storage-domain

Pure storage vocabulary and durable codecs for StromDB.

This crate owns the *spelling* of everything StromDB persists: the typed
identities of durable objects, their object-store key strings, and the byte
codecs that turn domain values into durable archives and back. It performs no
I/O. Protocol vocabulary lives one layer down in `strom-domain`; reading and
writing bytes lives one layer up in `strom-object-store` and the engine.


## Two worlds per durable type

Every durable type exists twice, and the pairing is deliberate:

- The **domain type** (`StreamPath`, `StreamRecord`, `Seal`, ...) is owned and
  proven valid. Its constructors are the trust boundary; after construction no
  consumer revalidates it.
- The **archived type** is either generated by `rkyv::Archive` or supplied by a
  private field adapter for protocol types such as `StreamPath`. It is a
  borrowed, unproven view into encoded bytes.
  Bytes that come back from storage are foreign data, whatever we wrote
  earlier, so archived values are never trusted directly.

The conversion from archived to domain is where the crate applies
"parse, don't validate" (see `docs/stromstyle.md`). Every decoder runs the
same gate pipeline, in cost order:

1. complete byte bound (`bounds.rs`, before any structural work)
2. structural access (`rkyv::access` with bytecheck; alignment-free)
3. identity cross-check against the durable location the bytes came from
4. resource bounds, checked before result allocation
5. domain validation and owned reconstruction, all-or-nothing

A decode failure is a `Result`, never a panic: contradictory durable bytes
are a failure, not a bug.

## Serialization decision: one family, rkyv

All durable objects use rkyv, and only rkyv. We deliberately do not mix
serialization formats, so there is one codec habit, one validation pattern,
and one fuzz surface. 

The objects in this crate are control-plane metadata: Seals, WAL runs,
Directory and Ledger rows. They are small, decode rarely (recovery and
bootstrap), and their consumers want owned, fully validated values. Their
decoders therefore always materialize owned domain values and never hold
archived views beyond the decode call.

This means the zero-copy capability of rkyv is intentionally *unused* here.
That is not an oversight, and it is not a reason to swap in a simpler owned
decode format: zero-copy in-place access is reserved for future data-plane
objects (record payloads), which will be large and hot. Keeping the
control plane on the same format means the data plane inherits a proven
boundary instead of introducing a second one.
