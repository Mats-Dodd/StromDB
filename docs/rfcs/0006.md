# 0006: paced WAL flushes, byte-bounded runs, and awaiting ingress capacity

This RFC gives the writer's WAL flush a pacing rule and a byte budget, and
turns buffer-capacity shedding into flow control. After this slice low-byte
sustained traffic is coalesced to a bounded interval-triggered object rate,
high-byte traffic flushes as soon as a buffer fills, the flush batch is sized
in the currency the object store bills, and saturation eventually applies
bounded backpressure instead of returning an error the caller can only retry.

It refines [`architecture.md`](../architecture.md) and RFCs 0004 and 0005,
and supersedes two of their provisional shapes:

- RFC 0004's flush-on-completion discipline is replaced. The writer no
  longer takes a new flight the instant the previous one lands; it takes a
  flight when the pacing rule, byte budget, or hard capacity says so.
- RFC 0004's buffer-capacity `Overloaded` refusal is deleted. Admission
  saturation becomes interpreter flow control over the bounded ingress
  channel. The refusal survives only for suffix-budget exhaustion, which
  RFC 0005's checkpoint trigger consumes as its shed signal — that arm is
  unchanged.

RFC 0005's "no clocks" principle is scoped, not repealed: no
materialization, checkpoint, or collection decision reads a clock, exactly
as before. This RFC introduces one monotonic clock seam in `strom-common` for
WAL flush pacing only. RFC 0005 deferred timer policy "if measurement ever
justifies one"; the justification here is arithmetic rather than measurement,
and it is given below.

## Decision

The writer paces time-triggered WAL flush starts with one rule — **minimum
spacing** — and bypasses that spacing for byte pressure and hard capacity:

```text
take a flight when pending facts exist, no flight is active, and
    ingress is draining                                (shutdown)
    or admission cannot take one worst-case fact       (hard full)
    or estimated pending bytes >= flush_buffer_bytes   (budget reached)
    or now - last flush start >= min_flush_interval    (spacing satisfied)
otherwise arm one timer for the remaining spacing
```

An all-idempotent pending barrier drains replies without a WAL flight. The
conditions above govern a barrier that contains at least one fact.

Five choices fix this shape:

1. **Minimum spacing, not linger and not a ticker.** Replies wait for
   durability (RFC 0004), so every flush delay is caller latency. A ticker
   or a linger delays the first command after idle by up to one interval
   for nothing. Minimum spacing is a token bucket holding one token: a
   partition whose last flush start is at least one interval old flushes its
   first command immediately, and sub-budget sustained traffic starts at most
   one interval-triggered flight per interval. A command arriving after a
   short quiescent gap still waits for the remainder of the spacing; resetting
   the spacing merely because the pending buffer became empty would defeat
   coalescing for trickle traffic. Byte-driven and hard-full flights may start
   sooner; this is adaptive coalescing, not a strict PUT-rate limiter.
2. **Coalescing low-byte traffic is the point.** Each RUN consumes one suffix
   coordinate from the 1024 budget, and a checkpoint starts at a span of 512
   (RFC 0005). Unpaced, a sub-budget 20-command-per-second trickle makes 20
   RUNs per second and forces a checkpoint every ~26 seconds forever. With a
   250 ms minimum interval the same trickle makes at most 4 RUNs per second
   and a checkpoint at most every ~128 seconds, with the same durability
   guarantee per reply. At high byte throughput the byte budget, rather than
   the interval, governs RUN and checkpoint cadence.
3. **The budget is bytes, and it flushes early.** Bytes are the currency
   the object store prices and the WAL object bound (4 MiB) is written in;
   a fact count is internal codec spelling and becomes meaningless when
   appends carry real payloads. A full buffer is a stronger signal than the
   time-coalescing window, so the budget overrides spacing. The budget is
   soft and estimated. Independently, the pending-command bound is proven not
   to exceed the existing `WAL_RUN_FACTS_MAX`, and the encoded WAL object
   bound remains hard; capacity at either boundary forces a flush regardless
   of any knob.
4. **One flight stays one flight.** Concurrent WAL PUTs would let a later
   batch become durable before an earlier one, and no reply can be released
   out of order, so pipelining buys buffering, not acknowledgement
   latency. The ceiling of the single-flight shape is one full RUN per PUT
   round trip — far above any load this slice serves. This is the
   TigerBeetle shape: the in-flight request is the batch window, and the
   next batch fills while it flies.
5. **Saturation is flow control, not an error.** When the pending buffer
   cannot take one more worst-case fact, the interpreter stops polling
   ingress. The public operation awaits send capacity on the bounded channel
   (1024), so saturation eventually applies bounded backpressure with no new
   error and no caller-side retry loop. Cancellation withdraws a send only
   while that send is still waiting for channel capacity. Once the send
   completes, the writer owns the queued command; cancelling the caller drops
   its reply waiter but does not retract the command. StromDB adds no internal
   enqueue deadline. Suffix exhaustion keeps its refusal because it means
   checkpointing cannot keep up, and an honest shed beats an unbounded wait.

## Scope

This RFC specifies:

- the minimum-spacing rule, its monotonic-instant plumbing, and its recovery
  initialization;
- the soft byte budget, its per-fact estimate, and the dominance proof
  obligations;
- the machine/interpreter split: the `ArmFlush` action, the `FlushDue`
  event, and the one-armed-timer discipline;
- ingress gating, awaited enqueue capacity, and the deletion of the
  buffer-capacity refusal;
- the idempotent-reply barrier under a waiting buffer;
- shutdown and recovery interaction; and
- the public knobs and their validation.

It does not specify append ingestion, any change to checkpoint triggers or
collection, multiple WAL flights, an explicit public flush call (replies
already wait for durability, so it would give the caller nothing), or
observability counters.

## Monotonic time enters as data

The machine stays pure (stromstyle §4). `WriterMachine::handle` gains a
`now: MonotonicInstant` argument; the machine never reads a clock. The
interpreter stamps every event from an injected `MonotonicClock` —
`OsMonotonicClock` in production, `ManualMonotonicClock` in deterministic
tests — so every pacing path is testable by advancing a manual clock.

The clock's sleep owns everything it needs and returns a `'static` future, so
the interpreter can retain one timer without borrowing the clock or making
`Writer` self-referential:

```rust
pub trait MonotonicClock: Debug + Send + Sync + 'static {
    fn now(&self) -> MonotonicInstant;

    fn sleep_until(
        &self,
        deadline: MonotonicInstant,
    ) -> Pin<Box<dyn Future<Output = ()> + Send + 'static>>;
}
```

The manual implementation clones shared, `Arc`-owned state into each returned
future. Production uses the same ownership shape even though its future needs
no shared mutable state.

`MonotonicInstant` is distinct from the Unix `Timestamp` used for wall-clock
domain meaning. Pacing never reads `SystemTime`: operating-system clock
correction cannot extend or bypass an interval, and the type system prevents
expiry time from being mixed with elapsed writer time.

The machine keeps `last_flush_started_at: Option<MonotonicInstant>`, set when
any flight is taken, including a byte-driven or hard-full flight. Recovery
initializes it to `None`, so the first flush after bootstrap is immediate: no
prior flush start exists, and spacing is vacuously satisfied.

## The pacing machinery

Two new vocabulary items:

```text
WriterAction::ArmFlush { deadline: MonotonicInstant }   immediate interpreter action
WriterEvent::FlushDue                                  one observation per arm
```

The discipline is zero-or-one armed timer, asserted like every other slot:

- `schedule` computes the flush condition above. When pending facts exist,
  no flight is active, ingress is open, hard capacity and the byte budget are
  unreached, spacing is unsatisfied, and no timer is armed, it emits
  `ArmFlush { deadline: last flush start + minimum spacing }` and marks the
  timer armed. `MonotonicInstant::saturating_add` defines that sum even for an
  extreme configured duration. The absolute deadline preserves the boundary
  derived from the event's stamped `now`; interpreter execution time cannot
  move it.
- The interpreter holds one timer slot. `ArmFlush` fills it with one
  owned `clock.sleep_until(deadline)` future; the sleep's completion sends
  `FlushDue`. The biased select order is completion-producing effects first,
  the flush timer second, and ingress third. A continuously ready ingress
  queue therefore cannot starve a due flush.
- `FlushDue` requires the armed marker, clears it, and re-runs `schedule`.
  It carries no other meaning: every flush condition is re-derived from
  current state, so a tick whose batch already flushed early through the
  byte budget simply finds nothing due and, at most, re-arms. No
  cancellation, epoch, or generation machinery exists.
- `IngressClosed` flushes pending facts immediately, ignoring spacing. A
  timer that fires while the writer is still draining clears its marker and
  finds nothing due. Terminal `Shutdown` may retain an armed marker: exiting
  the interpreter drops that inert sleep. Shutdown does not wait for or
  explicitly cancel a meaningless timer.

The output-bound constant `WRITER_OUTPUTS_PER_STEP_MAX` is re-proved with
the new action counted.

## The byte budget and its estimate

Admission tracks estimated encoded pending bytes incrementally:

```text
estimate(fact) = WAL_FACT_ENCODED_FIXED_BYTES_MAX
               + stream path byte length
               + content type byte length (create facts)

estimated pending bytes = WAL_RUN_FIXED_ENCODED_BYTES_MAX + sum(estimate)
```

The two constants live in `strom-storage-domain` `bounds.rs` beside encode
vectors that prove them, in the RFC 0005 pattern: each constant must dominate
the encoded contribution of its worst case. The estimate is therefore a sound
upper bound. Admission proves before receiving another command that one
worst-case fact would leave the estimate at or below
`WAL_ENCODED_BYTES_MAX`; an actual fact can cross the soft byte budget but
cannot cross the hard object bound.

The machine derives one exact hard-full predicate with checked arithmetic:

```text
hard full when
    pending command count == WRITER_PENDING_COMMANDS_MAX
    or estimated pending bytes + worst-case fact estimate
        > WAL_ENCODED_BYTES_MAX
```

`WRITER_PENDING_COMMANDS_MAX` is a distinct process-memory bound even when it
initially has the same value as `WAL_RUN_FACTS_MAX`: idempotent completions
consume a reply waiter but no durable fact. The compile-time relationship

```rust
const _: () = assert!(WRITER_PENDING_COMMANDS_MAX <= WAL_RUN_FACTS_MAX);
```

proves every pending barrier also satisfies the durable fact-count bound, so
the machine needs no redundant pending-fact counter or runtime branch. If the
two values ever genuinely diverge in the other direction, that change must
introduce the corresponding fact-count proof. Hard full bypasses spacing and
drains the pending barrier as soon as the active flight lands. If the barrier
contains facts it becomes the next flight; if it contains only idempotent
completions their replies are released without a WAL object.

## Awaiting ingress capacity

The machine exposes one readiness predicate: admission is open exactly when
the pending buffer is not hard full. The interpreter's select polls
`ingress.recv()` only while admission is open (and ingress is, as before,
open). The readiness predicate and hard-full flush condition are complements,
so the writer cannot stop polling ingress without also arranging the drain
that will reopen it. Consequences:

- The buffer-capacity branch of `AdmissionRefusal::Overloaded` is deleted,
  with its tests. `Engine::enqueue` becomes async and uses `send().await`
  rather than `try_send`; the public operation awaits it before awaiting its
  reply. A caller may enter the bounded channel immediately while it has room;
  once the channel fills, later callers await enqueue capacity. Cancelling a
  still-pending send relinquishes its place in the sender queue. A completed
  send transfers ownership to the writer, so later caller cancellation does
  not remove the command from ingress. No caller observes a new error state.
- Saturation is transient by construction: hard full forces a drain when no
  flight is active, or immediately after the active flight lands.
- The suffix-room refusal in `accept_fact` is untouched. It still sheds,
  still sets the checkpoint retry mark, and still feeds RFC 0005's shed
  trigger. The two saturations are different in kind: one is a PUT away
  from clearing, the other says the checkpoint pipeline is behind.

## The idempotent-reply barrier

Today an idempotent completion (a duplicate create, an already-closed
close) replies immediately whenever no flight is active, because pending
facts without a flight is a transient state under flush-on-completion.
Under pacing that state persists up to one interval, and an idempotent
reply must not outrun the fact it depends on: a duplicate create's
`AlreadyExists` may not be released before the original create is durable.
The rule becomes barrier-shaped:

```text
idempotent completion replies immediately  iff  no flight and no pending fact
otherwise it joins the pending barrier
```

An all-idempotent pending set still flushes no WAL and replies as one
batch, exactly as today.

## Knobs

`Db::open(store)` keeps its signature and its defaults. One options surface
with private, validated fields is added:

```text
Db::open_with(store, Options)

Options {
    min_flush_interval: Duration,   default 250 ms
    flush_buffer_bytes: usize,      default WAL_ENCODED_BYTES_MAX (4 MiB)
}

Options::default()
    .with_min_flush_interval(duration)
    .with_flush_buffer_bytes(bytes)?
```

`with_flush_buffer_bytes` returns a typed `OptionsError` for zero and values
above `WAL_ENCODED_BYTES_MAX`, so an invalid `Options` cannot reach
`Db::open_with`; configuration errors do not widen `OpenError`.
`min_flush_interval` of zero is legal and restores eager
flush-on-completion timing. It does not restore RFC 0004's buffer-capacity
refusal; awaited ingress capacity remains the admission policy. The options
thread `Db -> Engine::open -> spawn_writer` and reach the machine as plain
data. The `MonotonicClock` is injected beside `Entropy` at `Engine::open`;
`Db::open` and `Db::open_with` supply `OsMonotonicClock`.

| Policy | Value | Meaning |
| --- | ---: | --- |
| `min_flush_interval` | 250 ms | spacing for time-triggered starts; byte and hard-full starts bypass it |
| `flush_buffer_bytes` | 4 MiB | soft estimated-byte budget; flushes early |
| WAL flights | 0 or 1 | unchanged; one PUT in the air at most |
| armed flush timers | 0 or 1 | one sleep at most; ticks are re-evaluations |
| ingress channel | 1024 | unchanged; the bounded queue callers await when full |
| pending commands | 4096 | facts and idempotent reply waiters behind the active flight |

Both defaults are declared tunable after measurement. The spacing default
follows the arithmetic in decision 2; nothing in this RFC depends on the
exact values.

## Tests

### Pacing, on a manual clock

- A partition whose last flush start is at least one interval old flushes its
  next command with no delay; the following command inside the interval waits
  for the boundary.
- A command arriving after the writer became quiescent but before the spacing
  boundary still waits for the remaining interval.
- Under a steady generated load, every flush start is justified by shutdown,
  hard full, the byte budget, or spacing; no fifth condition starts a flight.
- Sub-budget steady load starts at most one interval-triggered flight per
  interval. Byte-driven flights may start sooner and reset the spacing origin.
- The budget flushes early inside the spacing window, and the later tick
  finds nothing due and re-arms at most once.
- At most one timer is armed at any point in any generated schedule; a
  `FlushDue` without the armed marker is a machine protocol violation.
- `min_flush_interval` zero reproduces eager flush-on-completion timing while
  retaining awaited ingress capacity.
- The first flush after recovery is immediate.

### Bytes

- Encode vectors prove `WAL_RUN_FIXED_ENCODED_BYTES_MAX` and
  `WAL_FACT_ENCODED_FIXED_BYTES_MAX` dominate their worst cases, so the
  running estimate dominates the real archive length on generated fact
  sequences.
- Hard capacity drains regardless of knob settings; construction refuses a
  knob above the object bound.
- Options construction accepts byte budgets at one and at the object bound,
  and refuses zero and one above the object bound.

### Admission

- A saturated writer stops polling ingress; queued callers make progress when
  the hard-full barrier drains; no caller observes a buffer-capacity error.
- A public operation awaits a full ingress channel, relinquishes its queued
  place when cancelled while waiting, and observes `Unavailable` if the
  channel closes while it waits.
- Once enqueue completes, cancelling the public operation drops its reply
  receiver but does not retract the command; the writer still decides it in
  ingress order.
- The suffix-room shed still refuses, still marks the checkpoint retry,
  and still triggers RFC 0005's checkpoint on shed.
- An idempotent completion behind a pending fact is not released before
  that fact's RUN is durable; at quiescence it is released immediately.

### Shutdown

- `IngressClosed` with a waiting buffer flushes it at once, ignoring spacing.
- A tick arriving while the writer drains is harmless; terminal `Shutdown`
  drops an armed timer without waiting for it.

## Alternatives not selected

**A flush ticker (the SlateDB shape).** SlateDB acknowledges writes before
durability, so its 100 ms ticker bounds durability staleness, not caller
latency. StromDB's replies wait for durability, so a ticker taxes every
low-load command by up to one interval. Minimum spacing gives the same
sub-budget coalescing without a recurring phase delay after a sufficiently
long idle period; a command arriving shortly after a flush still waits for
the remaining spacing.

**Linger (the Kafka producer shape).** `linger.ms` delays the first
command of every batch by construction. Same objection, smaller tax, still
pure loss at low load.

**A fact-count knob.** The count is internal codec spelling
(`WAL_RUN_FACTS_MAX` exists to make the encode proof simple), the layering
keeps storage spellings out of the public API, and the unit collapses when
appends carry real payloads. It survives as the internal hard anchor only.

**Concurrent WAL flights.** Out-of-order durability cannot release
out-of-order replies, so extra flights add sequencing machinery and buy
only buffering. The single-flight ceiling is not the binding constraint.

**A strict PUT-rate cap.** Making the interval unconditional would bound
request cost even under high byte throughput, but it would also cap one
partition's WAL throughput to `flush_buffer_bytes / min_flush_interval` and
hold a hard-full buffer idle. StromDB starts the next flight immediately when
byte pressure or hard capacity justifies it; operators can still bound the
time-triggered trickle rate with `min_flush_interval`.

**Always refuse, or always await.** Uniform refusal makes every caller
carry a retry loop for a state that clears in one PUT. Uniform awaiting
hides suffix exhaustion — a real "the checkpoint is behind" signal —
inside an unbounded wait. The split follows the difference in kind.

**Timer epochs and cancellation.** A generation-stamped timer protocol
guards against stale ticks that the spurious-safe re-evaluation makes
harmless. The armed marker is the entire protocol.

## Implementation slices

1. Add the distinct `MonotonicClock`, `MonotonicInstant`, production, and
   manual implementations to `strom-common`, including the owned
   `sleep_until` future. Thread the clock through `Engine::open` and
   `spawn_writer`; give `WriterMachine::handle` its `now` argument; update
   existing tests with explicit monotonic instants.
2. Add the encoded-estimate constants, their encode vectors, and
   `WRITER_PENDING_COMMANDS_MAX` to `strom-storage-domain`; prove its
   relationship to `WAL_RUN_FACTS_MAX`, add incremental byte accounting to
   admission, and define `hard_full` once.
3. Add pacing to the machine: `last_flush_started_at`, the armed marker,
   deadline-bearing `ArmFlush`, `FlushDue`, the idempotent barrier, and the
   deterministic pacing tests.
4. Add the interpreter timer slot, its explicit select priority, and ingress
   gating. Change public enqueue from `try_send` to awaited `send`; delete the
   buffer-capacity refusal and its tests.
5. Add `Options`, its validated builder, and `Db::open_with`; document the
   defaults.

Each slice keeps workspace metadata and lints inherited and passes
`just ci` before commit.

## Deferred

- Tuning `min_flush_interval` and `flush_buffer_bytes` from measurement, and
  deriving the spacing default from a target checkpoint period.
- Byte-budget admission for append payloads, when appends exist.
- A caller-visible admission-wait deadline, if server timeouts ever need
  one below the transport.
- Observability counters for flush starts, budget flushes, and gated
  ingress time.
