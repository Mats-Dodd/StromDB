# 0005: advancing checkpoints, the one-rule planner, and targeted collection

This RFC makes the resident forest durable-forward. It joins the running
writer from RFC 0004 to the materialized manifest from RFC 0003: checkpoint
flush, delta and full-base publication, and the first authorized garbage
collection. After this slice a partition can admit, checkpoint, recover its
admission headroom, and reclaim the WAL RUNs and SSTs that its own advances
made unreachable.

It refines [`architecture.md`](../architecture.md) and RFCs 0003 and 0004,
and supersedes four of their provisional shapes:

- RFC 0003's initial base-plus-deltas operational discipline is replaced.
  The eight-run high-water mark, the opportunistic same-cut full compaction,
  and the checkpoint/maintenance priority publication lane do not exist.
  Compaction is one branch inside the flush planner, not a publication mode.
- RFC 0003's "SST GC is not authorized by this RFC" is replaced by the
  birth-bounded reachability rule below, which authorizes exact targeted
  collection.
- RFC 0004's "no checkpoint yet" scope note is closed. The suffix gate is no
  longer a permanent read-only cliff; a successful advance restores
  admission.
- The architecture's exact-validator conditional WAL deletion is relaxed for
  this collector to an idempotent delete of a typed RUN proof. No conforming
  engine issues a WAL create at or below a published Seal cut; the complete
  argument is in the WAL RUN collection section. The validator stays on
  `AuthorizedWalRunDelete` as defense in depth against a non-conforming
  actor, and the conditional primitive may be restored inside the adapter
  without changing this RFC.

## Decision

The engine produces exactly one publication shape: the advancing Seal. The
writer coordinates one checkpoint flight; the diff, encode, and child
creates run in one spawned task. CPU preparation — the scan, diff, and
encode — runs through `spawn_blocking` or an equivalent bounded blocking
executor, and only the object creates run asynchronously, so ten million
rows never occupy a runtime worker that the writer's event loop depends on.
Every checkpoint follows one pipeline:

```text
trigger fires (writer loop)
-> freeze cut W and one O(1) forest snapshot
-> spawn the checkpoint task:
   diff against the retained base forest at cut P
   -> plan: one delta candidate, or one full base for every non-empty tree
   -> chunk rows into bounded tables under fresh identities
   -> make every child durable, or abandon the candidate
   -> send one advance Seal exactly once
-> Direct (writer loop): install, reopen admission, collect the dead set
```

Five choices fix this shape:

1. **One publication shape.** No producer for the `maintain` transition
   exists. `maintain` stays legal in the durable format for a later RFC, but
   no code constructs it. Run pressure only grows through advances, and every
   advance can flatten it, so a same-cut mode adds a candidate class without
   adding a capability.
2. **One binary plan.** The delta candidate carries unchanged trees exactly
   and prepends one run to each changed tree. When that complete candidate
   holds every hard bound, it publishes. Otherwise every non-empty tree is
   rewritten as a full base at W. The hard bounds are the planner's only
   inputs; there is no high-water knob, no scheduler, and no hybrid state.
3. **The diff is the flush.** The persistent forest makes the RFC 0003 flush
   set a structural comparison: `imbl::OrdMap::diff` between the base at P
   and the snapshot at W yields exactly the keys whose logical value changed,
   and skips shared subtrees. No dirty-key tracking and no second fold exist.
4. **Targeted collection only, one lane.** After a `Direct` advance the dead
   set is exact and locally known: the WAL coordinates the new cut covered,
   and the tables the source manifest carried but the successor dropped.
   Collection needs no LIST, no sweep, and no age guard. It occupies one
   zero-or-one collector slot; when the slot is busy, the advance's dead set
   is intentionally leaked. Orphans from abandoned candidates leak too, as
   requirement 8 permits.
5. **No clocks.** No materialization or collection decision reads a clock.
   Triggers are event-driven; retry pacing is traffic-driven. Timer-and-age
   collectors (the SlateDB shape) exist because their object names carry no
   relation to manifest history. StromDB's birth generations carry that
   relation, so age is unnecessary.

## Scope

This RFC specifies:

- flush row emission from the forest diff, for deltas and full bases;
- the binary delta-or-full-base planner and its progress guarantee;
- checkpoint cut selection, including the takeover FENCE cases;
- fresh-identity, attempt, and abandonment rules for checkpoint children;
- child and Seal evidence handling for the send-once candidate;
- writer integration: the one in-flight checkpoint, installation effects,
  admission recovery, and graceful shutdown;
- event-driven trigger policy;
- authorized WAL RUN collection, its deletion theorem for this slice, and
  the conditional-delete relaxation;
- authorized targeted SST collection, the birth-bounded reachability rule,
  and the bootstrap race argument; and
- model, property, fault, and recovery tests.

It does not specify same-cut maintenance production, orphan or leak sweeps,
adjacent-delta merging, Tally or Annals materialization, observability
hooks, protocol idempotency, or any timer machinery.

## Flush semantics

The checkpoint folds nothing. The writer's durable forest at cut W already
equals `fold(base at P, WAL prefix (P, W])`, because the writer folded each
durable RUN as it committed. The flush set is the structural diff between
the retained base forest and the frozen snapshot:

```text
Directory Add/Update -> the final Live or Tombstone row
Ledger    Add/Update -> the final Value row
Ledger    Remove     -> a Delete row in a delta; no row in a full base
```

This reproduces RFC 0003's flush table exactly. A stream created and hard
deleted wholly inside `(P, W]` produces one Directory tombstone row and no
Ledger row, because the Ledger key is absent on both sides of the diff. A
full base emits final values for every key and omits Ledger deletes, because
its interval reaches the oldest run.

The equivalence claim is normative: checkpoint output must equal strict fold
of the exact source through the exact selected prefix. The diff is an
implementation of that equation, not a second definition of it.

The base forest must be the state at exactly P. Bootstrap therefore retains
one snapshot of the merged forest before it replays the WAL suffix, beside
the replayed state it hands to admission. Diffing against the post-replay
forest instead would silently drop every replayed fact from the first
checkpoint after takeover.

## The planner

The planner has one precondition and two output shapes. The precondition is
`W > P`: no candidate is constructed when the selected cut equals the source
cut, so `candidate.replay.batch > source.replay.batch` never depends on
trigger-policy reasoning.

```text
delta candidate =
    carry every unchanged tree exactly
    + prepend one delta run to every changed tree

if the complete delta candidate holds every hard bound:
        TREE_RUNS_MAX per tree
        PARTITION_BOOTSTRAP_OBJECTS_MAX_V2 in aggregate
        PARTITION_BOOTSTRAP_BYTES_MAX_V2 in aggregate
    publish it
else:
    emit one full replacement base for every non-empty tree at W
```

The fallback is deliberately global. A fallback that rewrote only changed
trees could not guarantee progress: an unchanged but fragmented tree can
hold the aggregate above a bound by itself, and the checkpoint would then
fail forever while admission stays read-only. Rewriting every non-empty
tree restores the guarantee from RFC 0003's construction claim, re-proven
under encoded accounting by the constant assertion below: a complete
partition base at maximum logical capacity fits the aggregate bounds.
Progress is therefore unconditional, and the planner has no hybrid state.

An empty diff for a tree carries that tree exactly from the source Seal and
creates no run. A full Ledger base with zero values publishes the canonical
empty tree instead of an empty run. Directory cannot return to empty because
path occupancy is permanent.

Planner accounting uses encoded bytes, not resident logical bytes. The
existing logical constants (`DIRECTORY_ROW_LOGICAL_BYTES_MAX` and its
siblings) are resident-budget accounting and do not bound rkyv archive
output: a one-row Directory fixture encodes to 77 bytes against a 21-byte
logical estimate. The planner therefore uses dedicated encoded worst-row
constants:

```text
SST_ARCHIVE_FIXED_BYTES_MAX          fixed archive framing and identity
DIRECTORY_ROW_ENCODED_BYTES_MAX      one archived Directory row, aligned
LEDGER_VALUE_ROW_ENCODED_BYTES_MAX   one archived Ledger value row, aligned
LEDGER_DELETE_ROW_ENCODED_BYTES_MAX  one archived Ledger delete row, aligned

estimated table bytes = fixed archive bytes + sum(encoded worst-row bytes)

delta is legal in bytes when:
    carried exact TableRef.object_bytes
    + fresh estimated table bytes
    <= PARTITION_BOOTSTRAP_BYTES_MAX_V2
```

The constants live in `strom-storage-domain` beside encode tests that prove
them: each constant must dominate the encoded size contribution of its worst
row, and a constant assertion must keep the full-base construction claim
valid — a complete base at maximum logical capacity stays within the
aggregate byte bound under encoded accounting. Chunking uses the same
encoded accounting against the 64 MiB writer target, so one currency drives
both decisions and the plan is decided while it is still pure.

Exact `TableRef.object_bytes` values come from the freeze of each encoded
table, as RFC 0003 requires. A checked assertion confirms every exact length
is at most its proven encoded upper bound, and the encoder still proves the
hard 128 MiB object bound.

## Cut selection

W is the greatest durable batch at the moment the checkpoint starts: the
writer's last committed RUN, or the takeover FENCE when no RUN has committed
since Ready. W may be the takeover FENCE even when `(P, W]` contains RUN
facts: after takeover that span holds the replayed older-owner suffix below
the FENCE, and the ordinary fold and diff equations apply unchanged. The
zero-fact advance is the special case where `(P, W]` contains only FENCE
coordinates, so `snapshot(W) = base(P)` and
`logical(candidate) = logical(source)` is the correct fold of an empty fact
prefix. That special case is how a partition whose suffix was filled by
repeated recovery FENCEs drains that suffix.

The candidate replay point is `Through { batch: W, owner: claim owner }`.
Replay through the takeover FENCE ended at the claim owner, and every later
coordinate is authored by the claim owner, so the owner in force at any
selectable W is the claim owner.

The writer keeps admitting and committing while a checkpoint is in flight.
The snapshot is immutable; later facts stay in the suffix for a later
checkpoint.

## Identity, attempts, and publication failure

Fresh children carry `birth = candidate generation` and `owner_claim = the
generation of the writer's authored bootstrap claim`. One attempt counter
distinguishes candidates within the process; one ordinal distinguishes
tables within a candidate. `owner_claim < birth` holds because the head only
grows above the authored claim.

Children are content objects and use create-or-verify:

| Child evidence | Effect |
| --- | --- |
| `Direct` | durable |
| `DurableMatch` | durable; identical bytes at the fresh identity |
| `NotOurs` | durable contradiction; no actor may occupy a fresh identity |
| `Unresolved`, read matches | durable |
| `Unresolved`, foreign bytes | durable contradiction |
| `Unresolved`, absent or read fails | abandon the candidate; retryable |

The reconciliation read is one bounded exact GET compared byte-for-byte
against the frozen candidate table.

The advance Seal is sent exactly once:

| Evidence | Effect |
| --- | --- |
| `Direct` | install the checkpoint and continue as its author |
| `DurableMatch` | no continuing capability; the writer exits `Fenced` |
| `NotOurs` | fenced or contested; the writer exits `Fenced` |
| `Unresolved` | the writer exits `Poisoned`; bootstrap resolves history |

An abandoned candidate is never retried and never rebased. Its durable
children are unreachable orphans. The next trigger event proposes a fresh
candidate with fresh identities. There is no retry loop and no backoff
timer: trigger checks happen on commit and shed events, so failed
checkpoints pace themselves with traffic.

## Writer integration

The writer gains a second zero-or-one in-flight slot beside the WAL flight.
The slot holds one spawned checkpoint task; the writer's event loop only
freezes the snapshot, receives the evidence, and installs. Completion
priority is WAL flight first, checkpoint second, ingress last, because WAL
completion releases reply waiters.

Installing a `Direct` advance:

```text
head generation <- candidate generation
replay cut      <- W
base forest     <- the checkpoint snapshot
published view  <- new Seal identity, new cut, current durable forest
collector slot  <- filled with the exact dead set, or the set is leaked
```

The suffix-span admission gate reads the replay cut, so admission headroom
returns with the installation. Admitted state, the pending RUN, and reply
ordering are untouched; the checkpoint reads only durable state.

Graceful shutdown drains ingress, resolves the active WAL flight, and
resolves a checkpoint flight whose Seal create already began, because a
started conditional create cannot be read as non-publication (RFC 0003's
publication rule). A checkpoint task that has not yet sent its Seal is
abandoned like any other candidate. The sent-versus-not-sent boundary needs
a small handshake inside the task so cancellation cannot race the Seal
create; that handshake is an implementation detail of the slot. Shutdown
never waits for the collector slot; an interrupted collection leaks.

## Triggers

Trigger policy is named and changeable after measurement. A trigger check
runs on each commit event, on each shed event, and once at Ready:

```text
WAL_SUFFIX_CHECKPOINT_SPAN_TRIGGER = 512   (in bounds.rs; half the 1024 budget)

start a checkpoint when none is in flight and
    suffix span since the cut >= the trigger span
    or admission shed a command for suffix room
```

There is no timer. An idle partition below the trigger span starts no work.

## WAL RUN collection

This slice has no payload packs, so the architecture's WAL deletion theorem
reduces to the cut:

```text
a RUN at batch B is deletable iff B <= newest Seal replay batch
```

After installing a `Direct` advance from P to W, the collector visits each
coordinate in `(P, W]` in order, with one bounded read per coordinate:

```text
absent               -> continue; the coordinate is already collected
FENCE                -> continue; FENCEs are permanent by construction
RUN                  -> typed delete through ObservedWal::into_run_delete
read or delete fails -> stop and leak the remainder
```

Only the failure arm stops the pass. A FENCE refusal and an absent
coordinate are expected outcomes, never errors, so a permanent FENCE inside
the span cannot strand the RUNs behind it. The span is bounded by
`WAL_SUFFIX_COORDINATES_MAX_V2`, so no LIST is needed.

The delete is idempotent rather than exact-validator conditional. The
argument that no conforming engine reoccupies a collected coordinate has
three parts, and all three are needed — the fence-candidate clamp alone only
constrains successor claimants:

- The current writer allocates `next_batch` monotonically and never resends
  a classified WAL create, so it never issues a second create at or below
  its own published cut.
- A successor writer starts strictly above the inherited Seal cut and
  places its FENCE strictly above that cut, per the fence-candidate clamp.
- Therefore no conforming engine issues a WAL create at any coordinate `B`
  at or below a published cut. A replacement between the collector's
  observation and its delete requires a non-conforming actor, which is
  outside the correctness scope.

`AuthorizedWalRunDelete` still carries the validator so the adapter can
restore the conditional primitive without changing this seam.

The collector holds no durable cursor, occupies the one collector slot the
writer never waits on, and may leak. A leaked RUN below the cut is invisible
to recovery: bootstrap's fence-candidate clamp already tolerates collected
and surviving coordinates below the cut in any mixture.

## SST collection

Serving and recovery load only the newest Seal. Seal keys are permanent, but
the closure of a superseded Seal is not: only the newest Seal's children
must exist. Collection is therefore governed by reachability from the
newest head, bounded by birth generation:

```text
for a captured newest Seal H:
    dead(table) iff birth(table) <= H.generation
                and H does not reference table
```

Proof: the architecture's transition laws admit exactly three manifest
producers — a claim copies its source manifest exactly, and an advance or
maintain carries only source-carried or candidate-generation-fresh children.
Every legal Seal therefore carries only children of two kinds:
source-carried from its exact predecessor, or fresh with birth equal to its
own generation. By induction over successors of H, any table referenced by
any Seal newer than H with birth at most `H.generation` is reachable from H
itself. A table that H cannot reach and that cannot be born later is dead
forever. A stale capture of H only shrinks the dead set; it is never
unsafe. No age watermark, clock, or grace period participates. If a later
RFC adds a transition kind, it must re-prove this induction.

The proof covers a concurrent bootstrap. A contender Direct-creates its
manifest-copying claim before it loads any table (RFC 0004's phase order).
Either the contender's claim wins the next generation — then our advance is
fenced, never installs, and never collects — or our advance wins — then the
contender's claim create fails and it exits before its first table GET. No
execution loads a closure that this collector may delete.

The authorized mechanism is targeted only. After a `Direct` advance, the
installer computes the exact superseded set:

```text
dead set = tables(source Seal) - tables(successor Seal)
```

which is a subset of the theorem's dead set with the successor as H. The
collector deletes each with the idempotent content delete, in the same
silent, leak-permitted collector slot as the WAL span, with the same rule:
a failure stops the pass and leaks the remainder. A typed delete
authorization is constructible only from the source-and-successor manifest
pair, so no code path deletes a table from a raw key or a LIST result.

Orphans — children of abandoned or fenced candidates — are not collected in
this slice. A later RFC may add a bounded LIST sweep validated against the
same reachability rule.

## Bounds

This RFC adds no durable bound and no durable format change. The policy
defaults it names live in `strom-storage-domain` `bounds.rs`:

| Policy | Value | Meaning |
| --- | ---: | --- |
| `WAL_SUFFIX_CHECKPOINT_SPAN_TRIGGER` | 512 | suffix span that starts a checkpoint |
| SST table target | 64 MiB | chunk target under encoded worst-row accounting |
| candidate retry | none | abandoned candidates wait for the next trigger event |
| checkpoint flights | 0 or 1 | one spawned checkpoint task at most |
| collector slot | 0 or 1 | one collection task at most; a busy slot leaks the dead set |

## Tests

### Properties and models

- Checkpoint output equals strict fold of the exact source through the
  exact selected prefix, for deltas and for full bases, over generated
  histories.
- The diff-based flush set equals the RFC 0003 flush table on generated
  base/suffix pairs, including create-then-delete inside the window.
- A delta at each hard bound is legal; one beyond each bound flips every
  non-empty tree to a full base.
- The full-base fallback restores every bound even when an unchanged
  fragmented tree alone holds the delta candidate over an aggregate bound;
  planner progress is unconditional whenever `W > P`.
- The planner constructs no candidate when the selected cut equals the
  source cut.
- Full-base output never contains a Ledger delete; delta deletes never
  resurrect an older value under later merges.
- Each encoded worst-row constant dominates its worst row: an encode vector
  at maximum key, value, and identity sizes proves
  `DIRECTORY_ROW_ENCODED_BYTES_MAX`, `LEDGER_VALUE_ROW_ENCODED_BYTES_MAX`,
  `LEDGER_DELETE_ROW_ENCODED_BYTES_MAX`, and `SST_ARCHIVE_FIXED_BYTES_MAX`.
- A constant assertion proves a full base at maximum logical capacity fits
  `PARTITION_BOOTSTRAP_BYTES_MAX_V2` under encoded accounting.
- Chunking never exceeds the table target under encoded worst-row
  accounting, every frozen exact length is at most its proven encoded upper
  bound, and encoded tables never exceed the hard object bound.
- The targeted SST dead set never intersects the successor manifest, and no
  generated legal successor chain can reference a collected table.

### Recovery and publication

- Reopen after a delta checkpoint and after a full-base checkpoint equals
  the uninterrupted forest.
- The first checkpoint after a takeover flushes the replayed facts: its cut
  at the FENCE covers the older-owner RUNs below it, and the diff runs
  against the pre-replay base at P.
- A zero-fact advance through a FENCE-only suffix drains it and reopens
  admission.
- Crash or failure at every child and Seal boundary leaves the old Seal
  authoritative or the complete new Seal authoritative, never a mix; orphans
  from the failed candidate never become reachable.
- Every child evidence row in the table above produces its stated effect;
  `NotOurs` and foreign bytes at a fresh identity are contradictions, and an
  unresolved absence abandons the candidate as retryable.
- `DurableMatch`, `NotOurs`, and `Unresolved` Seal evidence exit the writer
  fenced or poisoned without a blind resend.
- Admission sheds at the suffix bound, a checkpoint installs, and admission
  resumes; reads stay available throughout.
- After WAL and SST collection, bootstrap succeeds; FENCEs survive
  collection; a coordinate collected below the cut never confuses the fence
  clamp.
- A collection pass continues past permanent FENCEs and absent coordinates,
  and stops only on a read or delete failure, leaking the remainder.
- A busy collector slot leaks the next advance's dead set and nothing else;
  collector tasks never accumulate past one.
- Graceful shutdown resolves a checkpoint whose Seal create began, abandons
  one that has not sent, and never waits for the collector slot.
- An injected collection failure leaks and changes nothing else.

## Alternatives not selected

**A same-cut maintenance producer.** Run pressure only grows through
advances, and the planner's full-base branch flattens it on the advance that
created it. A maintenance mode adds a second candidate class, a priority
lane, and abandonment rules for no capability this slice needs. The durable
`maintain` transition remains for a later RFC with a real same-cut workload.

**A high-water compaction mark.** An eight-run knob below the sixteen-run
hard bound only tunes when the full base happens. The hard bounds already
force it before any bound breaks, and fewer inputs make the planner total
and obvious.

**Timer-and-age garbage collection.** SlateDB lists directories on an
interval and keeps a minimum age because its object names cannot prove
deadness against manifest history. StromDB's birth generations can, so the
exact targeted set is deletable immediately, with no clock in the engine.

**Full-base-only (no deltas).** Trivially simple, but every checkpoint at
scale rewrites the complete base. The delta branch is one planner arm and
one row-emission difference, and the format already carries runs.

**A touched-trees-only fallback.** Rewriting only changed trees on aggregate
overflow cannot guarantee progress, because an unchanged fragmented tree can
hold the aggregate above a bound alone. The global fallback is the smallest
rule with an unconditional progress proof.

**Exact-measurement planning.** A first encode pass could measure exact
table lengths before legality is decided, at the cost of one table-sized
buffer and a second delta encode. The encoded worst-row constants prove a
conservative fit with no encode at all and keep the planner pure; exact
lengths still come from the freeze each table already requires. Logical
constants were not an option: they are resident accounting and do not bound
archive output.

**LIST sweeps for orphans and WAL leaks now.** Both are bounded and
compatible later, both are pure loss-recovery rather than correctness, and
requirement 8 explicitly permits the leak until then.

## Implementation slices

1. Retain the claim manifest and the pre-replay base forest at P in `Ready`;
   make the head generation and replay cut mutable writer state.
2. Add the table create seam (create-or-verify with the child evidence
   table) and the fresh-identity attempt allocator.
3. Add the encoded worst-row constants to `strom-storage-domain` with their
   encode vectors and the full-base constant assertion; then the pure
   planner: diff to rows, encoded-accounting chunking, the binary
   delta-or-full-base rule with the `W > P` precondition, and
   advance-candidate construction, with the fold-model and progress property
   tests.
4. Add the checkpoint task, writer integration, triggers, installation,
   admission recovery, and the shutdown rule, with reopen and fault tests.
5. Add the single-slot targeted WAL and SST collection task and its recovery
   tests.

Each slice keeps workspace metadata and lints inherited and passes `just ci`
before commit.

## Deferred

- Same-cut maintenance production and any compaction scheduler.
- Orphan and leak sweeps: bounded LIST traversal for tables, WAL RUNs below
  a historical cut, both validated against the reachability rule.
- Adjacent-delta merging and metadata-only concatenation of disjoint UID
  tables.
- Tally and Annals materialization, payload packs, and their collection
  proofs.
- Observability counters and operator hooks for collection outcomes.
- Any timer-driven policy, if measurement ever justifies one.
