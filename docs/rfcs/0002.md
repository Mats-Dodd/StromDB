# 0002: strom-storage-domain — durable vocabulary and codecs

> **Historical RFC; its codec is noncanonical.** StromDB has not shipped, and
> this RFC was never accepted as a compatibility contract. Every Postcard,
> Serde wire-type, envelope, CRC-32C, object-format version, and standalone
> Ledger-row codec rule below is superseded. Those sections remain only as
> design history and must not be implemented. The current boundary is
> [`../rkyv.md`](../rkyv.md): checked concrete rkyv roots, no content-format
> version, and explicit reconstruction through domain constructors. The crate
> layering, identities, key spelling, and semantic bounds survive only where
> the current architecture and code still carry them.

This RFC scopes a new crate, `strom-storage-domain`, holding the storage
engine's domain vocabulary and durable codecs for the first ledger slice:
Seal, WAL, and the simple-data ledger row. It refines
[`architecture.md`](../architecture.md) and supersedes it on one point (the
envelope decode gate order, below).

## Crate contract

- Pure: no I/O, no async, no object-store types. Domain newtypes, private
  wire types, codecs, and named bounds only.
- Depends on `strom-domain` (ledger rows reuse `StreamContentType`,
  `ExpiryPolicy`, `StreamLifecycle`, and the `StreamId` parser), plus
  `serde`, `postcard`, and `crc32c`.
- No dependency on `strom-object-store`. The adapter moves opaque bytes;
  this crate spells formats. The engine crate joins the two.
- A `proptest` feature exposes strategies, mirroring `strom-domain`.

```text
strom-domain          protocol vocabulary (parsed HTTP values)
      ^
strom-storage-domain  storage vocabulary + durable codecs   (this RFC)
      ^
engine crate (later)  typed stores, strict fold, correctness protocol
                      (also uses strom-object-store)
```

## Serialization stack

- Postcard, not bincode: compact, no self-description, suited to durable
  bytes.
- Serde names the field and variant order. Golden byte vectors define the
  real format; the derive code alone does not.
- Domain types implement `Serialize` only. Private wire types derive
  `Deserialize` only. Every decode ends in a domain constructor, so bad
  bytes cannot skip an invariant.
- Every decoder takes the typed identity with the bytes
  (`decode(&SealIdentity, bytes)`), so the key/body identity check cannot
  be skipped.
- Trailing bytes after the postcard body are an error: a noncanonical
  writer or silent format drift, never ignorable.

## The envelope for Seal and WAL objects

Frame layout:

```text
magic "STRM" (4) -> kind (1) -> version (1) -> postcard body -> CRC-32C (4, big-endian)
```

- The checksum coverage is normative, not inferred from vectors:
  `crc32c(magic || kind || version || postcard_body)`. The trailing four
  checksum bytes are excluded from their own coverage.
- CRC-32C (Castagnoli), matching the checksum already anchored in
  `strom-object-store` (RFC 3720 check value). One polynomial in the
  workspace.
- Kind 0 and version 0 stay reserved, so an all-zero header never looks
  valid.
- Versions are per kind: `(kind, version)` names a decoder. A later Seal
  bump does not touch WAL.
- Scope: the envelope wraps Seal and WAL objects only. SSTs and payload
  packs are designed around authenticated footer ranges and independently
  checksummed blocks (`architecture.md`, "sst format"); a mandatory
  whole-object trailing CRC has no clear relationship with range reads.
  The SST RFC decides its own container framing. Ledger rows inside an
  SST are frameless postcard; the container authenticates them.

Decode gate order is fixed on purpose:

```text
length    (bounded work before any parse; the bound covers the complete frame)
magic     (frame does not begin with STRM)
checksum  (bytes do not match their declared coverage)
kind      (unknown kind and wrong location share one error)
version   (upgrade path, not corruption)
body      (postcard, then domain constructors, then no trailing bytes)
```

Gate errors report the observed structure, never a claimed cause. Magic
is checked before the checksum, so a magic mismatch cannot distinguish a
foreign writer from bit rot; the error says what was observed.

This supersedes the decode order sketched in `architecture.md`, which
placed kind and format before the checksum. Checksum-first separates
corruption from a real object in the wrong place.

### Three versions, one relationship

Three distinct things carry the name "version":

1. The key-spelling namespace version: the `v1` segment inside durable
   keys.
2. The envelope version byte: the codec of one object kind.
3. `SealFormat`: the semantics of trees and comparators named by a Seal.

They move independently. One pairing rule is enforced at decode: Seal
envelope version 1 carries `SealFormat::V1` and nothing else. Any other
combination is a typed body error, so a mismatched pair cannot survive
decode.

## Bounded decode contract

Bounds gate work before parsing and hold on both sides: an encoder
returns a typed error rather than produce an over-bound frame.

| Bound | Value | Covers |
| --- | --- | --- |
| `SEAL_ENCODED_BYTES_MAX` | 1 MiB | complete Seal frame |
| `WAL_ENCODED_BYTES_MAX` | 4 MiB | complete WAL frame |
| `WAL_RUN_FACTS_MAX` | 4096 | facts in one run |
| `LEDGER_RECORD_BYTES_MAX` | 1 KiB | one frameless ledger row |

- Every byte bound covers the complete frame, including magic, header,
  and checksum — not merely the postcard body.
- The two WAL bounds are independent and both run: the fact-count gate never
  substitutes for the complete-frame byte bound. Slice-one domain values stay
  below 4 MiB at 4096 facts, but hostile frames are still byte-bounded and
  later fact variants must satisfy both limits.
- Sequence decode uses a custom serde visitor. It rejects a declared
  length hint above `WAL_RUN_FACTS_MAX` and stops before materializing
  fact `MAX + 1`. Postcard's declared sequence length never sizes an
  allocation.
- `WAL_ENCODED_BYTES_MAX` must stay at or below `PUT_BYTES_MAX` in
  `strom-object-store`. This crate cannot see that constant; the engine
  crate carries the `const` assertion relating them.
- The values are initial and revisable pre-alpha; each lives once in
  `bounds.rs` with its rationale.

## Identities and coordinates

| Type | Representation | Surface |
| --- | --- | --- |
| `PartitionId` | UUID (16 bytes), non-nil | spell/parse, hyphenated lowercase |
| `SealGeneration` | `NonZeroU64`, genesis = 1 | `get`, checked `successor()` |
| `BatchId` | `NonZeroU64` | `get`, checked `successor()` |
| `WalReplayPoint` | `enum { Genesis, Through { batch, owner } }` | `batch()` accessor; `Genesis` has none |
| `OwnerToken` | newtype over the authored claim's generation | compare only, no `get` |
| `StreamUid` | `NonZeroU64` | compare plus encode |

- `WalReplayPoint` folds the WAL cut and the replay owner into one value.
  Every real cut carries its owner, and `Genesis` with an owner is
  unrepresentable. This encodes the architecture's rule that `NoOwner` is
  legal only at cut zero, with no relational parse-time check left to
  forget. There is no separate `WalCut` or `ReplayOwner` type.
- `OwnerToken` wraps the claim generation: fence replay needs only strict
  increase, which claim generations give clock-free. The wrapper prevents
  mix-ups with `SealGeneration` at call sites.
- `StreamUid` is a partition-local counter. The create fact carries the
  absolute value; replay restores the allocator from the maximum seen.
- `PartitionId` is a newtype over 16 bytes with the canonical hyphenated
  lowercase spelling. It accepts every bit pattern except nil (all
  zeros), consistent with the reserved-zero convention; RFC 4122 version
  and variant bits are not restricted. Generation policy belongs to the
  shell with injected randomness; this crate only represents and spells
  it.

## Durable key spelling

Key spelling lives in this crate as pure string codecs with golden
vectors. The engine converts spellings into `ObjectKey` values; the
adapter never learns formats.

```text
partition/<uuid>/seal/v1/<reverse generation>
partition/<uuid>/wal/v1/<reverse batch>
```

Reverse coordinates are fixed-width 20-digit decimal encodings of
`u64::MAX - logical_ordinal`, so ascending `LIST MaxKeys=1` returns the
newest coordinate. The `v1` segment is the key-spelling namespace
version; it is independent of the envelope version byte and of
`SealFormat` (see "Three versions, one relationship"). The placeholder
keys in the object-store adapter tests (`p1`) are transport examples,
not canonical spellings; canonical spellings are anchored here.

## Seal

```rust
struct Seal {
    partition: PartitionId,
    generation: SealGeneration,
    replay: WalReplayPoint,
    format: SealFormat,   // V1, single variant for now
    ledger: TreeVersion,
    tally: TreeVersion,
    annals: TreeVersion,
}

enum WalReplayPoint {
    Genesis,
    Through {
        batch: BatchId,
        owner: OwnerToken,
    },
}
```

- `TreeVersion` is a unit-like domain type in this slice: its only value
  is the canonical empty tree. No structurally rich manifest exists whose
  constructors always reject content. The real range/run/`TableRef`
  structure arrives with the SST RFC and a Seal codec version bump.
- `SealFormat` is the semantic format of trees and comparators. The
  envelope version byte is the codec of the Seal object itself. Envelope
  version 1 pins `SealFormat::V1`; see "Three versions, one
  relationship".
- Parse-time invariant: partition and generation are cross-checked
  against the `SealIdentity` handed to the decoder. The replay-point
  relationship needs no check; the type carries it.

## WAL

```rust
enum WalObject {
    Run(WalRun),
    Fence(WalFence),
}

struct WalRun {
    partition: PartitionId,
    batch: BatchId,
    owner: OwnerToken,
    facts: BoundedNonEmptyVec<OperationFact>,
}

struct WalFence {
    partition: PartitionId,
    batch: BatchId,
    owner: OwnerToken,
}
```

- RUN and FENCE share one envelope kind; the decoder returns `WalObject`.
- This crate owns `BoundedNonEmptyVec`. Its bounds and the bounded
  sequence visitor are specified in "Bounded decode contract".

### Operation facts, slice one

```rust
enum OperationFact {
    StreamCreated {
        path: LedgerKey,
        uid: StreamUid,          // absolute; replay restores the allocator
        content_type: StreamContentType,
        expiry: ExpiryPolicy,
    },
    StreamClosed  { path: LedgerKey, uid: StreamUid },
    StreamDeleted { path: LedgerKey, uid: StreamUid },
}
```

Facts carry absolute guarded values. The `uid` in close and delete is the
cross-check strict fold uses to detect contradictions. Tally and Annals
effects join these variants in later slices. Strict fold itself lives in
the engine crate; this crate is vocabulary only.

## Ledger

```rust
struct LedgerKey(/* raw UTF-8 bytes of a canonical StreamId */);

enum LedgerRecord {
    Live(StreamRecord),
    Tombstone(PathTombstone),
}

struct StreamRecord {
    uid: StreamUid,
    content_type: StreamContentType,
    expiry: ExpiryPolicy,
    lifecycle: StreamLifecycle,   // Open | Closed
    created_at: BatchId,          // WAL coordinate of the create fact
}

struct PathTombstone {
    uid: StreamUid,               // the stream that died here
}
```

- `LedgerKey` is a distinct type from `StreamId`: raw path bytes preserve
  lexicographic path order for prefix scans. Construction is
  `From<&StreamId>`; decode reuses the one `StreamId` parser. Bound is
  `STREAM_ID_BYTES_MAX`.
- The path tombstone is a logical value variant, not an LSM delete
  marker, so compaction can never drop it by construction.
- `created_at` is derived at fold time from the coordinate at which the
  create fact folds; it is not stored inside the fact.
- The sliding-TTL deadline is not here. The policy is cold (Ledger); the
  moving deadline is hot (Tally).
- `SoftDeleted` becomes a third variant in the fork RFC; exhaustive
  matches will surface every touch point.
- Rows are frameless (see envelope section). The value does not repeat
  the path; the SST block pairs key and value, and `uid` gives a second
  identity anchor.

## Tests

- Golden vectors per kind: genesis Seal, claim Seal, one-fact run, fence,
  live ledger record, tombstone, each expiry variant. Vectors anchor the
  format independent of round trips.
- Per-gate corruption vectors: short frame, bad magic, one flipped bit,
  unknown kind, reserved version, trailing bytes, and a Seal frame whose
  envelope version and `SealFormat` disagree. Each decodes to a typed
  failure, never a partial value.
- Malformed key-spelling vectors: wrong digit count, coordinate zero,
  uppercase UUID, nil UUID, unsupported namespace version, and a reverse
  ordinal that spells a coordinate outside the typed space.
- Negative space: under `cfg(test)`, wire types also serialize, so tests
  write bodies no constructor accepts and assert typed body errors.
- Round-trip properties over proptest strategies; golden vectors remain
  the independent anchor.
- Order properties: `LedgerKey` byte order equals `StreamId` string
  order; reverse-ordinal spelling inverts coordinate order.
