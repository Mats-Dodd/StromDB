# 0003: four-store forest and authenticated SST v1

This RFC makes the first materialized StromDB forest real. It replaces the
unit-like `TreeVersion` from RFC 0002, promotes path resolution into its own
Directory store, makes Ledger UID-keyed, and defines the authenticated SST
container used by both stores.

It refines [`architecture.md`](../architecture.md) and supersedes two earlier
shapes:

- the Seal contains four peer trees, not three; and
- RFC 0002's path-keyed `LedgerRecord` becomes one Directory row plus one
  UID-keyed Ledger row.

There is no compatibility or migration requirement. Seal envelope version 2
and `SealFormat::V2` reject the earlier materialized shape. WAL version 1 is
unchanged because its current facts already carry the path and UID guards this
RFC needs.

The slice is complete when StromDB can write, publish, recover, replay, and
fully compact non-empty Directory and Ledger trees. Tally and Annals are named
by the same Seal but remain canonically empty until their own RFCs define their
rows.

## Decision

One partition is a four-store LSM forest committed by one Seal and advanced by
one WAL:

```text
external stream path
        |
        v
Directory: path -> Live(uid) | Tombstone(uid)
        |
        +------> Ledger: uid -> stream metadata
        +------> Tally:  uid-scoped current state       (deferred)
        `------> Annals: (uid, offset) -> retained row  (deferred)
```

Directory is the only durable store whose stream identity is a path. Ledger,
future stream-scoped Tally rows, future Annals rows, payload identities, and
fork lineage use `StreamUid`. A public request resolves its path once and
carries the resulting UID through the rest of admission and strict fold.

All stores share:

- one checksummed Seal and WAL correctness protocol;
- the range/run/table manifest shape;
- immutable content object identity;
- one authenticated SST container;
- newest-run-wins merge precedence; and
- bounded publication, recovery, and maintenance.

They do not share row codecs, filters, block targets, deletion policy, or
maintenance budgets merely for uniformity.

## Workload that fixes the shape

This is not a conventional cold-point-read LSM workload. Before a partition
becomes Ready, Directory and Ledger are reconstructed into resident state.
Admission resolves a path through resident Directory on every operation, but
does not issue an SST GET. The dominant durable read is a complete bootstrap
or recovery scan. The initial format therefore optimizes bounded sequential
construction, large contiguous reads, and scan decode throughput rather than
4 KiB point-read latency.

The two resident stores still have materially different rows and lifecycles:

- Directory keys are variable canonical paths, share prefixes, serve ordered
  enumeration, and remain occupied forever after a successful create.
- Ledger keys are dense monotonic UIDs. Creates dominate, arrive in UID order,
  records are wider than Directory rows, and close or hard-delete updates are
  comparatively rare.
- Protocol globs wildcard whole segments. Their literal leading segments map
  to one ordinary descendant-prefix scan, plus at most one exact-path
  candidate for a zero-segment `**`, so V1 needs no path-aware tree or
  separate glob index.
- Ledger deletion is real absence; Directory tombstones are permanent values.
  Combining them would force the larger record store to retain path strings
  and occupancy rows forever.

The object adapter contributes one non-negotiable format constraint:
`read_range` requires an expected CRC-32C before it issues a GET. A checksum
stored beside the requested block arrives too late. The Seal must authenticate
the footer span, and the verified footer must carry every child span and
checksum. This parent-carried chain is required by the I/O seam, not an
optional hardening feature.

SlateDB, `lsm-tree`, and TigerBeetle inform the resulting mechanics: shortened
sparse separators, restart-head prefix compression, newest-run precedence by
position, optional container sections, and workload-specific trees under one
commit point. Their policies are prior art rather than compatibility targets;
the StromDB WAL, Seal publication proof, adapter bounds, and bootstrap workload
remain authoritative.

## Scope

This RFC specifies:

- the four-tree Seal and its version relationship;
- dense partition-local UID allocation;
- Directory and Ledger durable vocabulary;
- current fact effects and cross-store invariants;
- the real one-range `TreeVersion` manifest;
- SST object identity, layout, footer, data blocks, and checksum chain;
- Directory block codec V1 and Ledger block codec V1;
- bounded bootstrap, flush, merge, and full compaction;
- initial writer policy; and
- golden, model, corruption, and recovery tests.

This RFC does not specify non-empty Tally or Annals rows, filters used by those
stores, payload packs, forks, soft deletion, subscription execution, SST
garbage collection, multiple ranges, general compression, or a generic
compaction scheduler.

## Crate contract

The existing layering remains:

```text
strom-domain
    protocol values such as StreamId, content type, expiry, lifecycle

strom-storage-domain
    Directory/Ledger vocabulary, manifest vocabulary, durable spellings,
    private wire types, bounded codecs

strom-object-store
    opaque immutable bytes, bounded whole reads, authenticated range reads,
    CRC-32C evidence

stromdb
    typed stores, strict fold, resident state, merge, flush, recovery,
    compaction, candidate Seal publication
```

`strom-storage-domain` remains pure: no I/O, async, adapter types, or engine
policy. The engine converts storage-domain authenticated spans into
`strom-object-store` ranges only after their parent has been verified.

No crate exposes a general-purpose key/value database API. `DirectoryStore`
and `LedgerStore` remain typed engine seams.

## Four peer trees

Seal envelope version 2 carries:

```rust
struct Seal {
    partition: PartitionId,
    generation: SealGeneration,
    replay: WalReplayPoint,
    format: SealFormat, // V2
    directory: TreeVersion,
    ledger: TreeVersion,
    tally: TreeVersion,
    annals: TreeVersion,
}
```

The physical stores are:

```rust
enum StoreKind {
    Directory,
    Ledger,
    Tally,
    Annals,
}
```

The canonical durable tags are `Directory = 1`, `Ledger = 2`, `Tally = 3`, and
`Annals = 4`. Zero stays reserved. Store names in object keys are lowercase
`directory`, `ledger`, `tally`, and `annals`.

Under `SealFormat::V2`:

- Directory and Ledger may be empty or non-empty;
- Tally and Annals must equal `TreeVersion::empty()`;
- Directory uses bytewise `DirectoryKey` order;
- Ledger uses numeric `StreamUid` order, spelled as big-endian bytes in SSTs;
  and
- any non-empty Tally or Annals manifest is a typed Seal-format error.

One Seal cut applies to all four trees. A checkpoint may change any supported
subset and carries every untouched tree exactly from its source Seal. A
same-cut maintenance Seal may replace the physical version of one tree while
carrying the other three unchanged.

## Stream UID allocation

`StreamUid` is a dense, monotonic, partition-local creation ordinal:

```text
first successful create has uid 1
each later successful create has previous maximum + 1
zero is reserved
an accepted UID is never reassigned to another path
```

Admission allocates a UID only for a create that becomes an
`OperationFact::StreamCreated`. If the containing WAL create is ambiguous, the
writer exits and recovery decides from durable evidence whether that fact
exists. A UID that never became durable and was never returned definitively is
not accepted and may be selected again after recovery.

Strict fold rejects a create whose UID is not the checked successor of the
current maximum. Exhausting `u64` rejects new create admission before fact
construction; it never wraps or saturates.

Directory retains one row for every accepted UID forever. Therefore the
recovered logical Directory obeys:

```text
Directory entry count == maximum allocated StreamUid
```

Genesis has no maximum UID and an empty Directory. This equality is a
cross-store and allocator recovery check, not a hint.

## Directory

Directory is the authoritative stream-path namespace:

```rust
struct DirectoryKey(/* raw UTF-8 bytes of one canonical StreamId */);

enum DirectoryEntry {
    Live(StreamUid),
    Tombstone(StreamUid),
}
```

`DirectoryKey` replaces `LedgerKey`. Construction from `&StreamId`, decoding,
maximum length, lexical order, and canonical path validation retain RFC 0002's
rules.

Directory has three observable states:

```text
row absent       path has never been accepted
Live(uid)        path resolves to this UID
Tombstone(uid)   path was accepted and remains permanently occupied
```

A Directory tombstone is an ordinary logical value. It is not an SST delete
marker and compaction never removes it. Directory SST decoding rejects a
physical delete cell.

Every accepted UID occurs in exactly one Directory row. A row may transition
once from `Live(uid)` to `Tombstone(uid)`. Its key never disappears and its UID
never changes. Directory logical entry count is consequently monotonic.

Directory serves:

- hot exact path resolution from resident state;
- permanent path-occupancy checks;
- ordered stream enumeration; and
- rare subscription backfill by ordered prefix scan followed by segment-glob
  matching.

Normal stream enumeration returns only `Live` rows. Occupancy checks retain
and inspect tombstones; subscription backfill does not surface them as
streams.

Protocol `*` and `**` are whole path segments. For a pattern, the literal
segments before its first wildcard form an ordered scan prefix. The scan still
runs the protocol glob matcher on every candidate; a prefix is only a bounded
candidate generator. A pattern beginning with a wildcard has an empty prefix
and may require a full Directory scan. Scheduling and pagination of that work
are deferred.

For a non-empty byte prefix `P`, the ordered candidate range is
`[P, successor(P))`. `successor` increments the last byte that is not `0xff`
and truncates after it; if no such byte exists, the upper bound is `Maximum`.
When a wildcard follows complete literal segments, the descendant prefix `P`
includes their trailing `/`, so `events/*` scans `events/` rather than the
wider `events` prefix. If the remaining pattern can match zero segments, as in
`events/**`, the exact key `events` is one additional point candidate. A
pattern with no wildcard is an exact lookup. Range bounds are comparator bytes
and need not themselves parse as stream paths.

Directory is not a disposable secondary index. It cannot be reconstructed
from Ledger after hard-deleted Ledger records disappear, and Ledger does not
repeat paths merely to manufacture that possibility.

## Ledger

Ledger stores cold stream identity and lifecycle by UID:

```rust
struct StreamRecord {
    content_type: StreamContentType,
    expiry: ExpiryPolicy,
    lifecycle: StreamLifecycle, // Open | Closed in this slice
    created_at: BatchId,
}
```

`StreamUid` itself is the Ledger key and is not repeated in `StreamRecord`.
The path lives only in Directory. Fork lineage and soft-deleted record variants
join Ledger in a later RFC.

The frameless `StreamRecord` Postcard wire uses the field order shown above
and reuses RFC 0002's content-type, expiry, lifecycle, and `BatchId` spellings.
It omits the old `LedgerRecord` outer variant and embedded UID. The standalone
path-keyed `LedgerRecord` and `PathTombstone` codecs are removed; no SST ever
published those pre-alpha row bytes.

Ledger cells may be:

```rust
enum Cell<Value> {
    Value(Value),
    Delete,
}
```

In this slice, `Delete` means that the stream record was hard-deleted. It
hides every older record for the UID. A compaction may omit the delete marker
only when its input reaches the oldest run, so no older record can reappear.

Ledger remains completely resident before Ready. Its durable SSTs optimize
bounded construction, full bootstrap scan, recovery, and compaction rather
than remote point GETs.

## Current fact effects

WAL envelope version 1 and the current fact wire remain unchanged:

```rust
enum OperationFact {
    StreamCreated {
        path: DirectoryKey,
        uid: StreamUid,
        content_type: StreamContentType,
        expiry: ExpiryPolicy,
    },
    StreamClosed { path: DirectoryKey, uid: StreamUid },
    StreamDeleted { path: DirectoryKey, uid: StreamUid },
}
```

The Rust source rename from `LedgerKey` to `DirectoryKey` does not change the
version-1 fact bytes. Golden WAL vectors must prove that claim.

Strict fold applies the following effects at fact coordinate `B`:

| Fact | Preconditions | Directory effect | Ledger effect |
| --- | --- | --- | --- |
| create | path absent; UID is maximum successor | `Live(uid)` | new open record with `created_at = B` |
| close | path is `Live(uid)`; Ledger record exists | none | absolute closed record |
| hard delete | path is `Live(uid)`; Ledger record exists | `Tombstone(uid)` | physical delete |

This is the current metadata-only storage slice, not the complete protocol fact
vocabulary. Its create fact always creates an open stream and carries no
payload. Closed-on-create, initial content, append, and atomic
append-and-close require an explicit later WAL fact-version decision; this RFC
does not encode them as an accidental sequence of independently meaningful
facts.

Normal admission constructs only facts that return `Applied`. Replay applies
the same strict reducer. A duplicate, no-op, path/UID mismatch, absent record,
UID gap, lifecycle regression, or rejected transition is a durable
contradiction during replay.

The fact is the atomic logical group. It is not legal to publish only its
Directory effect or only its Ledger effect. Tally and Annals have no effect in
this slice and remain empty.

## Cross-store invariants

The logical state at every V2 Seal cut and after every replayed fact obeys:

```text
every Directory UID is unique
every UID from 1 through maximum UID has exactly one Directory row
every Directory Live(uid) has exactly one Ledger value
every Ledger value has exactly one Directory Live(uid)
every Directory Tombstone(uid) has no Ledger value
Directory contains no physical deletes
Ledger contains no logical path tombstones
```

The last two live/tombstone relationships are specific to the no-forks slice.
A later soft-delete RFC must replace them explicitly rather than weakening
them by accident.

Bootstrap proves these relationships before constructing resident state. A
bounded UID bitmap is one suitable implementation: scan Directory to mark
seen/live UIDs and detect duplicates, then scan Ledger to consume exactly the
live set. The witness, not the bitmap representation, is normative.

```rust
struct LoadedForest {
    directory: ResidentDirectory,
    ledger: ResidentLedger,
    tally: LoadedEmptyTree,
    annals: LoadedEmptyTree,
}
```

`LoadedForest` can only be constructed after all tree-local and cross-store
checks succeed. `PublishedView` contains these four projections and the exact
post-Seal WAL overlay.

## Version relationship

The durable versions remain independent:

| Surface | Version in this RFC | Meaning |
| --- | --- | --- |
| Seal key namespace | `seal/v1` | canonical object-key spelling |
| Seal envelope | 2 | Seal body codec |
| `SealFormat` | V2 | four-tree semantics and comparators |
| WAL key namespace | `wal/v1` | canonical object-key spelling |
| WAL envelope | 1 | unchanged current fact codec |
| table key namespace | `table/v1` | canonical SST object spelling |
| SST child frame | 1 | data, footer, and reserved filter framing |
| Directory row codec | 1 | restart-head path blocks |
| Ledger row codec | 1 | fixed-UID blocks |

Seal envelope version 2 accepts only `SealFormat::V2`. The V2 Seal decoder
does not decode envelope version 1 as an empty approximation, and the V1
decoder does not accept a V2 body.

`SealFormat::V2` has durable numeric tag 2. The V2 private Postcard wire uses
the Seal and manifest field order shown in this RFC. Manifest `KeyBound` tags
are `Minimum = 1`, `Key = 2`, and `Maximum = 3`; zero is reserved. Domain
enums do not derive their durable representation implicitly: private wire
types translate every durable tag explicitly, and golden vectors anchor the
complete bytes.

The table key namespace version does not advance merely because a later SST
frame version is introduced. Object spelling and object contents are distinct
contracts.

## Table identity and spelling

SSTs are immutable content objects and use the architecture's fresh identity:

```rust
struct AttemptId {
    owner_claim: SealGeneration,
    local_counter: u64,
}

struct FreshIdentity {
    birth_generation: SealGeneration,
    attempt: AttemptId,
    ordinal: u32,
}

struct TableObjectId {
    fresh: FreshIdentity,
    store: StoreKind,
}
```

The key shape is:

```text
partition/<partition>/table/v1/<store>/<birth>/<owner>-<attempt>/<ordinal>
```

`birth`, `owner`, and `attempt` are zero-padded 20-digit decimal values.
`ordinal` is a zero-padded 10-digit decimal `u32`. `birth` and `owner` are
nonzero generations; attempt counter and ordinal may be zero. Store spelling
is the lowercase canonical name above. Parsers reject any alternate width,
sign, separator, case, extra segment, overflow, zero generation, or key/body
identity mismatch.

Example shape, with the UUID abbreviated only here:

```text
partition/<uuid>/table/v1/directory/
00000000000000000002/00000000000000000001-00000000000000000000/0000000000
```

Real golden vectors use a complete canonical UUID and one line.

`birth_generation` is the candidate Seal generation that may first select the
table. `owner_claim` identifies the directly authored claim under which the
attempt began. `local_counter` distinguishes attempts under that claim, and
`ordinal` distinguishes outputs within one attempt. A valid fresh identity has
`owner_claim < birth_generation`; all increments and comparisons are checked.

A retry freezes and create-or-verifies the same bytes at the same identity, or
starts a new attempt with fresh identities. It never adopts an arbitrary
orphan found by LIST or content hash.

## Manifest vocabulary

The real manifest is:

```rust
struct TreeVersion {
    ranges: BoundedNonEmptyVec<RangeVersion>,
}

struct RangeVersion {
    start: KeyBound,
    end: KeyBound,
    runs: BoundedVec<SortedRun>, // newest to oldest
}

enum KeyBound {
    Minimum,
    Key(Box<[u8]>),
    Maximum,
}

struct SortedRun {
    tables: BoundedNonEmptyVec<TableRef>,
}

struct TableRef {
    object: TableObjectId,
    footer: AuthenticatedSpan,
}

struct AuthenticatedSpan {
    offset: u64,
    length: NonZeroU64,
    checksum: Crc32c,
}
```

Span offsets are relative to the start of the table object. `end` is the
checked sum of `offset + length`, and `checksum` is CRC-32C over exactly that
span's bytes.

Ranges are half-open under the store comparator. `Minimum` is below every key
and `Maximum` is above every key. In `SealFormat::V2`, every tree has exactly
one range with `(Minimum, Maximum)` bounds. `Key` remains in the durable shape
so a later Seal format can define multiple ranges; V2 rejects it in a range
boundary.

The canonical empty tree has one full-keyspace range and no runs. An empty run
or empty table is illegal.

The checksummed Seal directly bounds every collection in the manifest. It
validates without fetching children:

```text
exactly one full range
runs newest to oldest by position only
every run non-empty
every table object has the enclosing StoreKind
every table birth_generation <= the enclosing Seal generation
every TableRef footer span is non-empty and arithmetically valid
every TableRef footer.length <= SST_FOOTER_BYTES_MAX
every TableRef footer.end <= SST_OBJECT_BYTES_MAX
every object identity occurs at most once in the complete Seal
all counts and encoded bytes remain below their named bounds
Tally and Annals equal canonical empty
```

Table key bounds, entry counts, block positions, and object byte length are
not duplicated in the Seal. They become trusted only after loading the
authenticated footer.

The loaded manifest additionally validates:

```text
every table's exact key range lies in its owning range
tables inside one run are ordered and key-disjoint
table footer StoreKind and object identity match the TableRef
all footer-derived counts and byte sums are checked
```

Only then may raw `TreeVersion` become `LoadedTreeVersion`.

## Initial bounds

Every encoder enforces the same bound as its decoder. Bounds cover complete
encoded regions, not only logical payloads.

| Bound | Value | Covers |
| --- | ---: | --- |
| `SEAL_ENCODED_BYTES_MAX` | 1 MiB | complete V2 Seal frame |
| `TREE_RANGES_MAX_V2` | 1 | the one full range |
| `TREE_RUNS_MAX` | 16 | hard runs per tree |
| `RUN_TABLES_MAX` | 4096 | tables in one run, also constrained by Seal bytes |
| `SST_OBJECT_BYTES_MAX` | 128 MiB | complete table object |
| `SST_FOOTER_BYTES_MAX` | 2 MiB | complete externally checksummed footer frame |
| `SST_BLOCKS_MAX` | 2048 | data blocks in one table |
| `SST_BLOCK_ENCODED_BYTES_MAX` | 1 MiB | complete data-block frame |
| `SST_BLOCK_DECODED_BYTES_MAX` | 2 MiB | materialized key and logical value bytes |
| `SST_BLOCK_ENTRIES_MAX` | 262144 | entries in one block |
| `SST_ENTRIES_MAX` | 16777216 | entries in one table |
| `DIRECTORY_KEY_BYTES_MAX` | 512 bytes | canonical stream path |
| `STREAM_RECORD_BYTES_MAX` | 1 KiB | one frameless Ledger value |

The 1 MiB Seal bound is also the hard aggregate manifest bound; local element
bounds never authorize an oversized Seal. A builder stops before adding an
element that would exceed any count, byte, or integer-representation limit.

Byte bounds run before Postcard parse. Every private wire sequence and byte
string uses a bounded visitor: an over-limit declared length is rejected
before allocation, and an indefinite or dishonest source is stopped before
materializing element `MAX + 1`. Wire values become domain values only after
all local and relational bounds pass.

These values are part of the V1 acceptance contract once this RFC is accepted
for durable use. Pre-alpha measurements may amend the RFC before that point;
writer targets may change afterward without changing decoder bounds.

Writer targets are smaller than hard decoder limits and are policy, not wire
semantics. Initial targets are 64 MiB of data per SST and 256 KiB encoded data
blocks for both resident stores. Measurements may change those targets without
a format bump.

`SST_OBJECT_BYTES_MAX` remains below the object adapter's PUT bound. The
engine carries constant assertions for bounds that cross crate ownership.
Deployment-specific resident capacity is a separate, explicit
`ResidentLoadBudget`; it may be lower than the format's finite structural
maximum but never raises a format bound.

## SST integrity model

The Seal-rooted checksum graph is mandatory for range reads:

```text
checksummed Seal
    `-- TableRef(object, footer span + expected CRC-32C)
            `-- verified footer
                    |-- block 0 span + expected CRC-32C
                    |-- block 1 span + expected CRC-32C
                    |-- ...
                    `-- optional filter span + expected CRC-32C
```

`strom-object-store::read_range` requires the expected checksum before issuing
the request. Therefore checksums cannot live only beside or inside the bytes
they protect. The parent must carry them. No range request is constructed from
an offset, length, or checksum learned from unverified remote bytes.

CRC-32C detects corruption, short reads, misdirected reads, and value confusion
under the current non-adversarial storage threat model. “Authenticated” in
this RFC means rooted expected integrity, not cryptographic authenticity. A
hostile-storage threat model requires a later cryptographic digest or MAC and
a format bump.

## SST object layout

SST V1 is one sequence of authenticated extents:

```text
offset 0
+-----------------------------+
| data block 0                |
+-----------------------------+
| data block 1                |
+-----------------------------+
| ...                         |
+-----------------------------+
| optional filter section     |  absent for Directory/Ledger V1
+-----------------------------+
| footer                      |  exact span named by TableRef
+-----------------------------+
object end == footer end
```

There are no inline CRC trailers, padding regions, or unclaimed bytes. Data
block spans are ordered, non-empty, contiguous, start at zero, and end at the
optional filter start or footer start. An optional filter ends at the footer
start. The footer is last, so the checked end of `TableRef.footer` is also the
exact object byte length.

Every checksum covers its complete encoded extent, including magic, kind,
version, fixed header, and body. Child checksums are not included as bytes
beside their children; they live only in the verified parent footer.

The framing discriminators are:

```text
magic "STRM" (4)
kind          (1): 3 = SST data block, 4 = SST footer, 5 = SST filter
version       (1): 1
body          (remaining bytes in the authenticated span)
```

Unlike Seal and WAL envelopes, child frames have no trailing internal
checksum. Their expected checksum comes from the parent. Footer and block
decode order is:

```text
authenticated span arithmetic and hard byte bound
-> expected CRC-32C over the complete span
-> magic
-> kind
-> version
-> bounded body with no trailing bytes
-> domain and key/body identity invariants
```

For a range read, the adapter establishes the CRC gate before returning
`VerifiedRangeBytes`. For a bounded whole-object read, the engine verifies the
footer slice and each child slice before parsing that slice.

## Footer V1

The footer body is a private Postcard wire refined into:

```rust
struct SstFooter {
    partition: PartitionId,
    object: TableObjectId,
    store: StoreKind,
    row_codec: RowCodec,
    entries: NonZeroU64,
    key_min: Box<[u8]>,
    key_max: Box<[u8]>,
    blocks: BoundedNonEmptyVec<BlockRef>,
    filter: Option<FilterRef>,
}

struct BlockRef {
    lower_bound: Box<[u8]>,
    span: AuthenticatedSpan,
    entries: NonZeroU32,
    decoded_bytes: NonZeroU32,
}

struct FilterRef {
    policy: NonZeroU16,
    span: AuthenticatedSpan,
}

enum RowCodec {
    DirectoryV1,
    LedgerV1,
}
```

The durable tags are `DirectoryV1 = 1` and `LedgerV1 = 2`; zero stays
reserved. The footer fields above occur in exactly that order in its private
Postcard wire.

`FilterRef.policy` is an on-disk compatibility identifier, not a runtime
configuration slot. A reader may use a negative filter result only when the
active `SealFormat` names the exact policy implementation for that ID,
including its hash family and extraction semantics. An unknown policy is a
typed format error. Directory V1 and Ledger V1 writers must set
`filter = None`; their decoders reject a present filter under
`SealFormat::V2`.

The footer decoder cross-checks:

```text
partition == the enclosing Seal and durable object key
object identity == TableRef object
store == owning Seal field and TableObjectId store
row codec is legal for store
entries == checked sum(block.entries)
key_min <= key_max under the store comparator
key_min, key_max, and every lower_bound are non-empty and store-bounded
every Ledger bound is exactly eight bytes
block lower bounds are strictly increasing and the first equals key_min
block spans and optional section cover exactly [0, footer.offset)
footer end == exact object bytes
all decoded byte claims and counts remain bounded
```

`SstFooter.entries` and `BlockRef.entries` count physical cells, including
Ledger `Delete` cells. `BlockRef.decoded_bytes` uses one representation-neutral
accounting rule:

```text
Directory row = full path bytes + one entry-tag byte + eight UID bytes
Ledger Value  = eight UID bytes + frameless StreamRecord bytes
Ledger Delete = eight UID bytes
```

It is not a claim about Rust heap layout. A block reader tracks and
cross-checks the actual sum before yielding a complete block.

`key_min` and `key_max` are exact table keys. `BlockRef.lower_bound` is a
search separator, not necessarily the exact first key of its block. Exact
table bounds must decode as store keys. A shortened lower bound is only a raw
comparator byte string and need not be UTF-8 or a canonical `DirectoryKey`.

For block zero, `lower_bound` is the exact table minimum. For each later
Directory block it is the canonical shortest byte string satisfying:

```text
previous block actual maximum < lower_bound <= current block actual minimum
```

Given ordered `previous` and `current`, the canonical separator is `current`
through the byte immediately following their common prefix. If `previous` is
a prefix of `current`, it is `current[..previous.len() + 1]`. Ledger block
lower bounds are the exact first eight-byte UID keys; shortening fixed keys is
not useful.

The writer validates separator relationships from actual block bounds. A full
bootstrap decoder recomputes and cross-checks them while it already scans all
blocks. Point and range planning trust only a verified footer produced by the
canonical writer.

After decoding every block, the full-table validator also proves:

```text
each block's actual keys are strictly ordered and duplicate-free
adjacent blocks' actual key ranges are strictly ordered and disjoint
the first and last actual keys equal footer key_min and key_max
the decoded entry and byte totals equal the footer claims
every lower_bound is the canonical separator for its actual neighbors
```

This closes the distinction between authenticated metadata and truthful
metadata: a checksum proves which bytes were published, while these checks
prove that those bytes describe the table that the manifest claims.

## CRC composition and range coalescing

CRC-32C composes over concatenation:

```text
crc(A || B) = crc32c_combine(crc(A), crc(B), len(B))
```

Because authenticated child spans are physically contiguous and contain no
inline checksum trailers, the engine can derive the expected checksum for any
contiguous sequence of blocks without reading their bytes. Composition is
left-to-right and uses the exact encoded length of every suffix span.

The object-store checksum vocabulary gains one checked composition operation.
It rejects a suffix length that cannot fit the implementation target and is
tested against direct CRC calculation over concatenated bytes.

A coalesced range read proceeds:

```text
select adjacent verified BlockRefs
-> combine their expected CRCs
-> construct one enclosing ByteRange
-> adapter verifies the combined CRC
-> split at the authenticated child boundaries
-> verify each child CRC again
-> decode each block
```

The aggregate check satisfies the adapter contract. Rechecking children is
cheap, localizes corruption, and detects a splitting or ordering bug. Transfer
window size, read-ahead, and concurrency are runtime policy.

## Directory data block V1

A Directory block frame body is:

```text
store tag = Directory                 u8
row codec tag = DirectoryV1           u8
block ordinal, zero-based             u32 big-endian
entry count                           u32 big-endian
restart interval                      u16 big-endian
entry bytes                           variable
restart offsets                       restart_count * u32 big-endian
restart count                         u32 big-endian
```

The initial writer uses restart interval 16. The decoder accepts a bounded
nonzero interval encoded in the block; the interval is not an ambient reader
setting. Entries `0, interval, 2 * interval, ...` are exactly the restarts, and
`restart_count == ceil(entry_count / interval)`. The encoded offsets must name
those entries and no others.

Each entry is:

```text
shared path bytes with restart head    u16 big-endian
path suffix bytes                      u16 big-endian
entry tag                              u8: 1 = Live, 2 = Tombstone
StreamUid                              u64 big-endian
path suffix                            declared bytes
```

At a restart, `shared == 0` and the suffix is the full key. Between restarts,
`shared` is measured against that interval's restart-head key, not the
immediately previous key. One entry can therefore be materialized from the
restart head without reconstructing a chain. The canonical writer uses the
complete longest common prefix with the restart head, and the decoder
recomputes it; multiple byte spellings of one row are not accepted.

Restart offsets are relative to the first entry byte. They are strictly
increasing, the first is zero, every target begins a complete entry, and every
restart entry has `shared == 0`. The trailer and entry area account for the
entire codec body with no trailing bytes.

Decode validates before yielding a row:

```text
frame and decoded-size bounds
store, codec, and ordinal cross-check
entry count == BlockRef.entries
entry and restart counts
offset arithmetic
shared length <= restart-head length
suffix and complete key length bounds
canonical DirectoryKey parse
strictly increasing keys with no duplicates
nonzero StreamUid
materialized key/value byte sum == BlockRef.decoded_bytes
exact decoded entry count and byte consumption
```

`Live` and `Tombstone` are both values. Tag zero, unknown tags, and any physical
delete representation are invalid.

## Ledger data block V1

A Ledger block uses fixed keys and a columnar body:

```text
store tag = Ledger                    u8
row codec tag = LedgerV1              u8
block ordinal, zero-based             u32 big-endian
entry count                           u32 big-endian
UID keys                              entry_count * u64 big-endian
cell tags                             entry_count * u8
value offsets                         (entry_count + 1) * u32 big-endian
value bytes                           variable
```

Cell tags are `1 = Value` and `2 = Delete`; zero and every other value are
reserved. Offsets are relative to the start of `value bytes`, begin at zero,
are nondecreasing, and end at the exact value-byte length.

For `Value`, adjacent offsets delimit one non-empty frameless Postcard
`StreamRecord` bounded by `STREAM_RECORD_BYTES_MAX`. For `Delete`, adjacent
offsets are equal and no value bytes exist. Values do not repeat their key.

Decode validates:

```text
frame and decoded-size bounds
store, codec, and ordinal cross-check
entry count == BlockRef.entries
entry count and all array-size arithmetic before slicing
strictly increasing nonzero UIDs
legal cell tags
offset monotonicity and final value length
Delete has zero value bytes
Value has one canonical, bounded StreamRecord with no trailing bytes
materialized key/value byte sum == BlockRef.decoded_bytes
exact body consumption
```

The contiguous UID array permits binary search without parsing values. There
is no prefix compression, restart interval, LSM sequence number, storage
timestamp, or per-row checksum. `StreamRecord.created_at` remains logical
stream metadata.

## Filters and general compression

Directory and Ledger are completely reconstructed before Ready. Their hot
point reads and prefix scans use resident state, so remote Bloom filters do not
avoid useful GETs. Both V1 writers omit the optional filter section.

The SST container has one authenticated optional filter slot so a later
`SealFormat` can use the same physical shape for a remote store. The filter's
exact hash family, target extraction, encoding, and false-negative prevention
belong to the RFC that first permits a non-empty filtered store.

The optional extent, when a later format permits it, uses the reserved SST
filter frame kind 5. This RFC fixes only that outer discriminator. The first
filter policy RFC must define its body, policy cross-check, bounds, and decode
gates before any writer may emit it.

Directory restart-head prefix truncation is part of its row codec. General
block compression is not. SST V1 accepts no Snappy, LZ4, Zstd, dictionary, or
ambient compression setting. Adding one requires an explicit encoded codec
identifier, decoded-size bound, checksum-over-encoded-bytes rule, and format
decision after measurement.

## Logical tree value

For one full range, a tree's logical value is newest-run-wins:

```text
for key K:
    inspect runs from newest to oldest
    the first Value or Delete is authoritative
    no cell means absence
```

One run contains at most one cell per key. Tables inside the run are ordered
and key-disjoint, so at most one table in that run can contain a key.

Directory rejects Delete, so its result is either absent, `Live`, or
`Tombstone`. Ledger Delete resolves to logical absence after hiding every older
value.

An implementation may recover by k-way merge, by scanning oldest to newest
and overwriting resident state, or by another bounded algorithm. It must
produce the same value and run no unbounded fan-out.

## Bootstrap and reads

Only a direct claimant loads admission-resident state. For each Directory and
Ledger table it may use one bounded whole-object GET:

```text
TableRef.footer.end gives the exact object-byte expectation
-> require footer.end <= SST_OBJECT_BYTES_MAX
-> whole read with ByteBound(footer.end)
-> require actual body length == footer.end
-> verify the footer slice against TableRef.footer.checksum
-> decode and validate the footer
-> verify each child slice against its footer checksum
-> decode blocks in key order
```

The whole object is raw evidence until those checks succeed. No child header,
length, count, or offset is parsed before its expected checksum passes.

Before any table GET, the claimant checked-sums every `TableRef.footer.end`
against its `ResidentLoadBudget` physical-byte and object-count limits. Within
each returned object it verifies the footer, adds its entry and decoded-byte
claims to the checked running totals, and rejects an over-budget table before
materializing that table's rows. Peak source work is therefore bounded by the
resident budget plus one bounded table object; it does not require retaining
the complete SST source set in memory.

A capacity refusal leaves the partition Unready but does not relabel otherwise
valid durable bytes as corruption. Placement may retry only on a worker with a
sufficient explicit budget; recovery never skips tables or falls back to an
older Seal.

Bootstrap validates every footer and the complete run/table structure, merges
both logical stores, and proves the cross-store invariants. It then replays the
exact WAL suffix through the same strict fold. Readiness requires the resulting
four-store `LoadedForest`; absence, corruption, an over-bound source, or a
contradiction cannot be treated as an empty tree or an older convenient state.

Runtime Directory and Ledger reads are resident. The durable RFC requires:

- exact Directory lookup;
- ordered Directory prefix iteration;
- exact UID Ledger lookup; and
- immutable published views.

It does not select `BTreeMap`, packed sorted vectors, a hash accelerator, a
dense vector, a segmented vector, local files, or NVMe as the resident
representation.

## Flush

For checkpoint prefix `(P, W]`, strict fold computes final absolute state for
each touched key at exactly cut `W`. Directory always emits its final value.
Ledger emission is relative to logical state at source cut `P`:

```text
Directory: final Live or Tombstone for each changed path
Ledger:    final Value different from source -> Value
           final absence with a source value -> Delete
           final state equal to source -> no cell
```

In particular, a stream created and hard-deleted wholly inside `(P, W]`
produces a permanent Directory tombstone but no Ledger cell. A repeated
idempotent lifecycle effect also need not produce a redundant value.

The builder independently sorts and deduplicates each store, writes bounded
tables, and groups the tables into at most one new newest run per touched tree.
An untouched tree is copied exactly. An empty effect set does not create an
empty run or table.

All output identities use the candidate generation and one named attempt.
Every child is create-or-verified durable before the candidate Seal is
encoded. Only the conditional creation of the complete Seal publishes the
Directory and Ledger effects together. If any child preparation fails, no
partial logical state exists; already-written children are unreachable
orphans.

The checkpoint builder must not observe state above `W`. Later accepted WAL
facts remain only in the post-Seal suffix until a later checkpoint.

## Initial base-plus-deltas policy

The durable manifest contains only ordered runs; it has no level, base, or
bottom tag. Initial maintenance uses the following operational discipline:

```text
runs = [newest delta, ..., oldest delta, materialized base]
```

Genesis is an implicit empty base. The first flush from genesis is a complete
base for the state at that cut. Later checkpoint flushes prepend deltas.

The hard manifest limit is 16 runs per tree. The initial scheduler begins a
full compaction before publishing a ninth run and may compact earlier under a
named encoded-delta-byte or bootstrap-object budget. A candidate that would
exceed the hard limit is rejected before child construction.

Full compaction selects every run in the one range and emits one replacement
run:

- newer input wins for duplicate keys;
- every Directory key is emitted as its final logical value;
- final Ledger values are emitted;
- final Ledger deletes are omitted because the selected interval reaches the
  oldest run; and
- output tables are newly identified immutable objects.

If the selected Ledger state is empty, full compaction publishes the canonical
empty tree instead of an empty replacement run. This is possible when every
created stream has since been hard-deleted. Directory cannot return to empty
after its first successful create because path occupancy is permanent.

The same-cut maintenance Seal carries the unchanged logical cut and other
three trees. It changes physical view identity through its new generation.

Adjacent-delta merging is legal under the same precedence rules but is not
required initially. The scheduler, thresholds, table reuse, and concurrency
are policy rather than durable format semantics.

Ledger UID creation is append-majority, not perfectly disjoint: one flush can
contain an old UID lifecycle update and a high-UID creation suffix. Separating
those bands into distinct tables and carrying disjoint suffix tables through
compaction is deferred until measurement justifies the extra planner.

## Failure and publication rules

SST objects carry no authority until selected by a Seal. Their writer may use
content-object create-or-verify at one fresh identity. It may not overwrite a
different occupant, select a partially written object, or manufacture success
from LIST.

Preparation order between touched stores is not a transaction protocol. The
required order is only:

```text
freeze each bounded candidate exactly once
-> make every selected child durable or abandon the candidate
-> encode one complete Seal from verified child identities
-> conditionally create the exact successor Seal
```

An ambiguous child result is reconciled against the frozen bytes. An ambiguous
Seal result follows the Seal protocol from the architecture and never causes a
blind resend. On fencing or poison, readiness is revoked and a fresh bootstrap
decides from durable evidence.

SST GC is not authorized by this RFC. Orphans and superseded tables may leak.

## Tests

### Golden formats

- V2 genesis Seal with four canonical empty trees.
- V2 Seal with one Directory run and one Ledger run.
- Canonical table-object key for every StoreKind.
- Directory footer and one/multiple-block tables.
- Ledger footer with Value and Delete blocks.
- Directory block with more than one restart interval.
- WAL V1 vectors proving the `LedgerKey` to `DirectoryKey` source rename did
  not change bytes.

Golden vectors are independent byte constants, not encode-then-decode tests.

### Decode gates and corruption

- Over-bound object, footer, block, count, key, value, or decoded-size claim.
- Footer or block CRC mismatch before body parse.
- Bad magic, kind, version, StoreKind, RowCodec, identity, or ordinal.
- Future table birth, owner claim not older than birth, or duplicate object
  identity.
- Footer not at object end; gaps, overlaps, reordering, zero-length spans, or
  arithmetic overflow.
- Incorrect table count/minimum/maximum or block-entry sum.
- Noncanonical or unsafe shortened separators.
- Unknown Directory tag, Directory physical delete, malformed path, duplicate
  path, or unsorted path.
- Zero, duplicate, or unsorted Ledger UID; bad offsets; value bytes on Delete;
  empty or malformed Value.
- Trailing bytes at every framing layer.

Every failure is typed and constructs no partial durable domain value.

### Properties and models

- CRC composition equals direct CRC over arbitrary concatenated bounded byte
  slices and is associative in physical order.
- Directory block encode/decode preserves arbitrary sorted canonical maps.
- Ledger block encode/decode preserves arbitrary sorted UID cell maps.
- Separator construction always satisfies the routing inequality and is
  deterministic.
- Arbitrary legal run stacks equal a simple newest-wins map model.
- Full compaction preserves the logical Directory and Ledger values.
- Directory compaction never decreases entry count or changes a UID.
- Ledger deletes never resurrect an older value.
- Dense UID creation, close, and delete histories preserve every cross-store
  invariant.
- Prefix candidate scans plus the protocol glob matcher equal a full-scan glob
  model, including the exact literal path when a terminal `**` matches zero
  segments.

### Recovery and publication

- Reopen from non-empty Directory and Ledger SSTs and reconstruct the same
  resident forest.
- Replay a WAL suffix over the loaded base and compare with uninterrupted
  strict fold.
- Crash/failure at every child-preparation boundary leaves either the old Seal
  authoritative or the complete new Seal authoritative, never a mixed forest.
- Missing or corrupt current children prevent Ready.
- A physical, object-count, entry-count, or decoded-byte load budget is
  exceeded before Ready without exposing partial resident state.
- Same-cut full compaction changes physical identity without changing logical
  state.

Tests use pure model transitions wherever I/O cannot add evidence. Adapter
contract tests separately prove bounded whole reads, authenticated range
reads, exact checksum mismatch behavior, and create-or-verify observations.

## Alternatives not selected for V1

**Keep path and record in one Ledger tree.** This retains wide path keys in
the larger object store, makes permanent occupancy dictate record retention,
and couples prefix-scan encoding to UID lifecycle access. The single Seal
already provides atomic publication across two trees, so the split does not
need a second transaction protocol.

**Build a dedicated glob index now.** Whole-segment glob syntax already gives
Directory a lexical descendant prefix and at most one exact-path candidate. A
fifth tree adds write and bootstrap work before evidence shows that candidate
filtering is a bottleneck. A segment-inverted index remains a compatible later
forest member.

**Add Bloom filters to the resident stores.** They cannot save an admission
GET because those lookups are resident. V1 keeps the authenticated optional
section but writes it absent, avoiding a second SST container when Annals
later supplies the remote point-read workload that justifies a filter.

**Store checksums beside blocks.** The range adapter cannot fetch a block until
its expected checksum is known. Inline trailers therefore cannot authorize
their own GET and are rejected in favor of the Seal-to-footer-to-block chain.

**Start with small pages and generic leveled compaction.** Bootstrap wants
large contiguous transfers, while one base plus bounded deltas already covers
the create-heavy resident trees. Multiple ranges, leveling, and sophisticated
scheduling add durable and operational states needed by Annals, not by this
slice.

**Use separate SST containers for resident and remote stores.** Store-specific
row codecs and optional authenticated sections preserve workload specialization
without duplicating framing, integrity, manifest, and corruption machinery.
