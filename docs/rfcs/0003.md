# 0003: four-store forest and sequential SST v1

> **Historical RFC; its codec is noncanonical.** StromDB has not shipped, and
> this RFC was never accepted as a compatibility contract. Every hand-written
> SST header, prefix encoding, row frame, Postcard body, checksum, envelope,
> `SealFormat`, and object/row-codec version rule below is superseded. Those
> sections remain only as design history and must not be implemented. The
> current boundary is in [`../architecture.md`](../architecture.md): checked
> concrete roots for Seal, WAL, Directory SST, and Ledger SST, with no
> content-format version and no standalone `StreamRecord` codec. The four-tree
> model, identities, bounds, ordering, and semantic invariants remain current
> only where the architecture and code still carry them.

This RFC makes the first materialized StromDB forest real. It replaces the
unit-like `TreeVersion` from RFC 0002, promotes path resolution into its own
Directory store, makes Ledger UID-keyed, and defines the deliberately small
SST format used to bootstrap both resident stores.

It refines [`architecture.md`](../architecture.md) and supersedes three
earlier provisional shapes:

- the Seal contains four peer trees, not three;
- RFC 0002's path-keyed `LedgerRecord` becomes one Directory row plus one
  UID-keyed Ledger row; and
- the architecture's footer-authenticated, block-addressable SST is deferred
  until a store has a measured remote-read workload that needs it.

There is no compatibility or migration requirement. Seal envelope version 2
and `SealFormat::V2` reject the earlier materialized shape. WAL version 1 is
unchanged because its current facts already carry the path and UID guards this
RFC needs.

The slice is complete when StromDB can write, publish, recover, replay,
checkpoint, and fully compact non-empty Directory and Ledger trees. Tally and
Annals are named by the same Seal but remain canonically empty until their own
RFCs define their rows and physical read paths.

## Decision

One partition is a four-store LSM forest committed by one Seal and advanced by
one WAL:

```text
external stream path
        |
        v
Directory: path -> Live(uid) | Tombstone(uid)
        |
        +------> Ledger: uid -> stream metadata
        +------> Tally:  uid-scoped current state       (deferred)
        `------> Annals: (uid, offset) -> retained row  (deferred)
```

Splitting the old path-keyed Ledger is a workload boundary, not normalization
for its own sake. The namespace half is a comparatively small, permanently
growing set with variable-length path keys, hot resident resolution, and rare
ordered prefix scans; the object half contains wider records behind fixed
eight-byte UIDs, is dominated by creation in UID order, and may physically
discard hard-deleted records. Keeping them together would make bulky records
pay for path prefix encoding and permanent tombstone retention, while forcing
one row and compaction policy onto two unlike access patterns. Separate
Directory and Ledger trees let each use the key layout, codec, and lifecycle
its workload wants, while their shared WAL fact and Seal preserve atomicity.

Directory is the only durable store whose stream identity is a path. Ledger,
future stream-scoped Tally rows, future Annals rows, payload identities, and
fork lineage use `StreamUid`. A public request resolves its path once and
carries the resulting UID through the rest of admission and strict fold.

All four stores share:

- the existing Seal and WAL authority protocol;
- the range/run/table manifest vocabulary;
- immutable content-object identities;
- newest-run-wins merge precedence; and
- bounded publication, recovery, and maintenance.

Directory and Ledger additionally share one small whole-object SST header.
They do not share row codecs or deletion policy. Tally and Annals do not
inherit this SST format before their workloads are specified.

## Workload that fixes the shape

This is not a conventional cold-point-read LSM workload. Before a partition
becomes Ready, Directory and Ledger are reconstructed into resident state.
Admission resolves a path through resident Directory on every operation, but
does not issue an SST GET. The dominant durable read is a complete bootstrap
or recovery scan.

Complete RAM residency is an initial serving requirement, not merely a cache
preference. Path resolution and stream-state validation participate in every
group-commit admission decision. An S3 read on that path would import network
availability and tail latency into acknowledged-write p99. V1 therefore makes
the complete Directory and Ledger locally answerable from RAM before Ready.
S3 remains the only source of durability.

The initial format therefore optimizes bounded sequential construction and
decode rather than point-read latency:

- one bounded whole-object GET per table;
- one forward pass over each table;
- no footer read;
- no sparse block index;
- no restart table;
- no Bloom filter; and
- no application-level SST checksum hierarchy.

The two resident stores still have materially different rows and lifecycles:

- Directory keys are variable canonical paths, share prefixes, serve ordered
  enumeration, and remain occupied forever after a successful create.
- Ledger keys are dense monotonic UIDs. Creates dominate, arrive in UID order,
  records are wider than Directory rows, and close or hard-delete updates are
  comparatively rare.
- Protocol globs wildcard whole segments. Their literal leading segments map
  to an ordinary descendant-prefix scan over resident Directory, plus at most
  one exact-path candidate when terminal `**` matches zero segments.
- Ledger deletion is real absence; Directory tombstones are permanent values.
  Combining them would force the larger record store to retain path strings
  and occupancy rows forever.

The reference engines remain useful prior art for tree separation, ordered
runs, prefix encoding, and compaction economics. Their block-oriented remote
point-read paths do not bind this resident-checkpoint workload.

## Scope

This RFC specifies:

- the four-tree Seal and its version relationship;
- dense partition-local UID allocation;
- Directory and Ledger durable vocabulary;
- current fact effects and cross-store invariants;
- the real one-range `TreeVersion` manifest;
- immutable table identity and exact object-length references;
- one fixed SST header and two sequential row codecs;
- bounded whole-object bootstrap, flush, merge, advancing full-base
  checkpoints, and same-cut compaction;
- the ten-million-lifetime-path partition capacity;
- aggregate bootstrap-source and post-Seal replay bounds;
- mutation backpressure when checkpoint progress is blocked;
- the initial base-plus-deltas writer policy; and
- golden, model, malformed-input, and recovery tests.

This RFC does not specify non-empty Tally or Annals rows, payload packs, forks,
soft deletion, subscription execution, SST garbage collection, multiple
ranges, remote SST point reads, range GETs, blocks, footers, sparse indexes,
filters, compression, encryption, or an SST checksum or digest.

## Crate contract

The existing layering remains:

```text
strom-domain
    protocol values such as StreamId, content type, expiry, lifecycle

strom-storage-domain
    Directory/Ledger vocabulary, manifest vocabulary, durable spellings,
    private wire types, bounded codecs

strom-object-store
    opaque immutable bytes, conditional-create evidence, bounded whole reads

strom-storage-engine
    typed stores, strict fold, resident state, merge, flush, recovery,
    compaction, candidate Seal publication

strom-db
    the embeddable public interface over the engine
```

`strom-storage-domain` remains pure: no I/O, async, adapter types, or engine
policy. `strom-object-store` does not decode an SST or return a type claiming
that table bytes are authenticated. The engine joins a typed `TableRef`, an
object key, raw bounded bytes, and the correct row decoder.

No crate exposes a general-purpose key/value database API. `DirectoryStore`
and `LedgerStore` remain typed engine seams.

## Existing correctness model is unchanged

This RFC changes the physical projection selected by a Seal. It does not add
or replace a correctness protocol.

Every checkpoint and maintenance publication continues to obey the exact
transition laws from the architecture:

```text
candidate.generation = source.generation + 1

advance:
    logical(candidate) = fold(logical(source), selected WAL prefix)

maintain:
    logical(candidate) = logical(source)

both:
    candidate children = source-carried or candidate-generation-fresh
```

Every fresh child is durable before the candidate Seal is attempted. One
conditionally created complete Seal publishes all four tree versions. Only a
caller that receives `CreateEvidence::Direct` for that exact successor Seal
may continue as its author. Maintenance remains tied to its exact source and
is never rebased. Orphans are never adopted through LIST.

Directory and Ledger do not need a cross-tree transaction record, a second
commit protocol, a path-to-record commitment, or a durable publication
witness. One `OperationFact` folds into both logical trees at one WAL
coordinate, and one Seal selects both physical trees at one generation.

Static SST decoding proves that selected bytes are bounded, well formed,
ordered, and mutually consistent. It cannot and need not reconstruct the
history that produced them. The writer and maintenance model tests prove the
transition equations; recovery applies the authoritative newest Seal and the
strict WAL fold. Checksums would not prove those transition equations.

## Four peer trees

Seal envelope version 2 carries:

```rust
struct Seal {
    partition: PartitionId,
    generation: SealGeneration,
    replay: WalReplayPoint,
    format: SealFormat, // V2
    directory: TreeVersion,
    ledger: TreeVersion,
    tally: TreeVersion,
    annals: TreeVersion,
}
```

The physical stores are:

```rust
enum StoreKind {
    Directory,
    Ledger,
    Tally,
    Annals,
}
```

The canonical durable tags are `Directory = 1`, `Ledger = 2`, `Tally = 3`, and
`Annals = 4`. Zero stays reserved. Store names in object keys are lowercase
`directory`, `ledger`, `tally`, and `annals`.

Under `SealFormat::V2`:

- Directory and Ledger may be empty or non-empty;
- Tally and Annals must equal `TreeVersion::empty()`;
- Directory uses bytewise `DirectoryKey` order;
- Ledger uses numeric `StreamUid` order, spelled as big-endian bytes in SSTs;
  and
- any non-empty Tally or Annals manifest is a typed Seal-format error.

One Seal cut applies to all four trees. A checkpoint may change any supported
subset and carries every untouched tree exactly from its source Seal. A
same-cut maintenance Seal may replace the physical version of one tree while
carrying the other three unchanged.

## Stream UID allocation

`StreamUid` is a dense, monotonic, partition-local creation ordinal:

```text
first successful create has uid 1
each later successful create has previous maximum + 1
zero is reserved
an accepted UID is never reassigned to another path
```

Admission allocates a UID only for a create that becomes an
`OperationFact::StreamCreated`. If the containing WAL create is ambiguous, the
writer exits and recovery decides from durable evidence whether that fact
exists. A UID that never became durable and was never returned definitively is
not accepted and may be selected again after recovery.

Strict fold rejects a create whose UID is not the checked successor of the
current maximum. V2 additionally rejects creation of a new path when the
successor would exceed `PARTITION_PATH_OCCUPANCIES_MAX_V2`. Both gates run
before UID allocation, fact construction, or WAL admission. The counter never
wraps or saturates.

Directory retains one row for every accepted UID forever. Therefore the
recovered logical Directory obeys:

```text
Directory entry count == maximum allocated StreamUid
Directory entry count <= PARTITION_PATH_OCCUPANCIES_MAX_V2
```

Genesis has no maximum UID and an empty Directory. This equality is a
cross-store and allocator recovery check, not a hint.

## Partition lifetime capacity

Every successfully accepted new path consumes one Directory occupancy for the
remaining lifetime of the partition. Closing, deleting, or expiring the stream
does not return that capacity. V2 fixes the lifetime bound at ten million
occupancies:

```rust
const PARTITION_PATH_OCCUPANCIES_MAX_V2: u64 = 10_000_000;
```

At the bound, admission rejects a create for a previously unseen path with a
typed partition-capacity refusal before assigning a UID or writing a WAL fact.
The refusal is permanent for that partition: a retry is useful only after the
router selects another partition or the control plane changes placement, not
against the same route. Existing streams remain readable and mutable, subject
to ordinary lifecycle and checkpoint-lag admission. Idempotent requests for an
existing live path retain their normal semantics. A full partition stays
Ready; it does not accept a fact that can make its next bootstrap impossible.

The capacity counts lifetime path occupancies, not currently live streams.
Future routing may place new paths in another partition, but neither routing
nor deletion may reclaim a V2 Directory path.

## Directory

Directory is the authoritative stream-path namespace:

```rust
struct DirectoryKey(/* raw UTF-8 bytes of one canonical StreamId */);

enum DirectoryEntry {
    Live(StreamUid),
    Tombstone(StreamUid),
}
```

`DirectoryKey` replaces `LedgerKey`. Construction from `&StreamId`, decoding,
maximum length, lexical order, and canonical path validation retain RFC 0002's
rules.

Directory has three observable states:

```text
row absent       path has never been accepted
Live(uid)        path resolves to this UID
Tombstone(uid)   path was accepted and remains permanently occupied
```

A Directory tombstone is an ordinary logical value. It is not an SST delete
marker and compaction never removes it. Directory's row codec has no physical
delete tag, so an illegal state is not representable.

Every accepted UID occurs in exactly one Directory row. A row may transition
once from `Live(uid)` to `Tombstone(uid)`. Its key never disappears and its UID
never changes. Directory logical entry count is consequently monotonic.

Directory serves:

- hot exact path resolution from resident state;
- permanent path-occupancy checks;
- ordered stream enumeration; and
- rare subscription backfill by ordered prefix scan followed by segment-glob
  matching.

Normal stream enumeration returns only `Live` rows. Occupancy checks retain
and inspect tombstones; subscription backfill does not surface them as
streams.

Protocol `*` and `**` are whole path segments. For a pattern, the literal
segments before its first wildcard form an ordered resident scan prefix. The
scan still runs the protocol glob matcher on every candidate; a prefix is only
a bounded candidate generator. A pattern beginning with a wildcard has an
empty prefix and may require a full Directory scan. Scheduling and pagination
of that work are deferred.

For a non-empty byte prefix `P`, the ordered candidate range is
`[P, successor(P))`. `successor` increments the last byte that is not `0xff`
and truncates after it; if no such byte exists, the upper bound is `Maximum`.
When a wildcard follows complete literal segments, the descendant prefix `P`
includes their trailing `/`, so `events/*` scans `events/` rather than the
wider `events` prefix. If the remaining pattern can match zero segments, as in
`events/**`, the exact key `events` is one additional candidate. A pattern
with no wildcard is an exact lookup.

Directory is not a disposable secondary index. It cannot be reconstructed
from Ledger after hard-deleted Ledger records disappear, and Ledger does not
repeat paths merely to manufacture that possibility.

## Ledger

Ledger stores cold stream identity and lifecycle by UID:

```rust
struct StreamRecord {
    content_type: StreamContentType,
    expiry: ExpiryPolicy,
    lifecycle: StreamLifecycle, // Open | Closed in this slice
    created_at: BatchId,
}

enum LedgerCell {
    Value(StreamRecord),
    Delete,
}
```

`StreamUid` is the Ledger key and is not repeated in `StreamRecord`. The path
lives only in Directory. Fork lineage and soft-deleted record variants join
Ledger in a later RFC.

The frameless `StreamRecord` Postcard wire uses the field order shown above
and reuses RFC 0002's content-type, expiry, lifecycle, and `BatchId` spellings.
It omits the old `LedgerRecord` outer variant and embedded UID. The standalone
path-keyed `LedgerRecord` and `PathTombstone` codecs are removed; no SST ever
published those pre-alpha row bytes.

`LedgerCell::Delete` is the LSM absence marker for a fully deleted stream
record. It hides every older record for the UID. A compaction may omit the
delete only when its input reaches the oldest run, so no older value can
reappear. It does not by itself authorize deletion of Annals or payload
objects; their later garbage collector must prove its own reachability rules.

Ledger remains completely resident before Ready. Its durable SSTs optimize
bounded construction, full bootstrap scan, recovery, and compaction rather
than remote point GETs.

## Protocol deletion and reclamation

The [Durable Streams Protocol](../durable-streams-protocol.md#soft-delete-and-lifecycle)
separates closing a stream from deleting it and requires a deleted source to
remain internally readable while a fork references it. Section
[5.4](../durable-streams-protocol.md#54-delete-stream) requires soft deletion
when the reference count is nonzero. The storage reclamation condition is
therefore:

```text
Ledger metadata and stream-owned data are reclaimable
    iff (deleted or expired) and inbound fork references == 0
```

Closing is never a deletion condition: a closed stream remains readable.
Retention may remove old extents according to policy while a stream remains
live, but does not remove the stream identity. Expiry uses the same inbound-
reference guard as explicit deletion because a fork may outlive its source.

When the condition holds, Directory becomes `Tombstone(uid)`, Ledger becomes
logically absent, and later Annals and payload collectors may reclaim the
stream's data. When the stream is deleted or expired with inbound references,
Directory still becomes `Tombstone(uid)`, Ledger retains a future
unavailable-but-pinned lifecycle record (`SoftDeleted` for explicit deletion),
and its data remains available only for fork reads. When the final reference
disappears, cleanup may cascade up a soft-deleted fork chain as the protocol
permits.

This RFC implements only the no-forks slice, in which the inbound reference
count is always zero. Its current `StreamDeleted` fact may therefore produce a
Ledger `Delete` directly. Fork creation, expiry facts, reference counts,
`SoftDeleted`, cascading cleanup, and physical data collection remain deferred,
but a later RFC must preserve the condition above. Permanent Directory
tombstones deliberately strengthen the protocol's recommendation that a
deleted URL not be reused and make occupancy independent of asynchronous data
collection.

## Current fact effects

WAL envelope version 1 and the current fact wire remain unchanged:

```rust
enum OperationFact {
    StreamCreated {
        path: DirectoryKey,
        uid: StreamUid,
        content_type: StreamContentType,
        expiry: ExpiryPolicy,
    },
    StreamClosed { path: DirectoryKey, uid: StreamUid },
    StreamDeleted { path: DirectoryKey, uid: StreamUid },
}
```

The Rust source rename from `LedgerKey` to `DirectoryKey` does not change the
version-1 fact bytes. Golden WAL vectors must prove that claim.

Strict fold applies the following effects at fact coordinate `B`:

| Fact | Preconditions | Directory effect | Ledger effect |
| --- | --- | --- | --- |
| create | path absent; capacity remains; UID is maximum successor | `Live(uid)` | new open record with `created_at = B` |
| close | path is `Live(uid)`; Ledger record exists | none | absolute closed record |
| hard delete | path is `Live(uid)`; Ledger record exists; no inbound forks by construction | `Tombstone(uid)` | logical `Delete` |

This is the current metadata-only storage slice, not the complete protocol
fact vocabulary. Its create fact always creates an open stream and carries no
payload. Closed-on-create, initial content, append, and atomic
append-and-close require an explicit later WAL fact-version decision.

Normal admission constructs only facts that return `Applied`. Replay applies
the same strict reducer. A duplicate, no-op, path/UID mismatch, absent record,
UID gap, lifecycle regression, or rejected transition is a durable
contradiction during replay.

The fact is the atomic logical group. It is not legal to publish only its
Directory effect or only its Ledger effect. Tally and Annals have no effect in
this slice and remain empty.

## Cross-store invariants

The logical state at every V2 Seal cut and after every replayed fact obeys:

```text
every Directory UID is unique
every UID from 1 through maximum UID has exactly one Directory row
every Directory Live(uid) has exactly one Ledger value
every Ledger value has exactly one Directory Live(uid)
every Directory Tombstone(uid) has no Ledger value
```

These live/tombstone relationships are specific to the no-forks slice. A
later soft-delete RFC must replace them explicitly rather than weaken them by
accident.

Bootstrap proves these relationships before constructing resident state. It
must validate counts, UIDs, and the explicit resident budget before any
allocation indexed by a decoded UID; a syntactically valid huge UID never
drives an unbounded dense allocation. A bitmap, ordered merge, or bounded map
may implement the check. The invariants, not the representation, are
normative.

```rust
struct LoadedForest {
    directory: ResidentDirectory,
    ledger: ResidentLedger,
    tally: LoadedEmptyTree,
    annals: LoadedEmptyTree,
}
```

`LoadedForest` can only be constructed after all tree-local and cross-store
checks succeed. `PublishedView` contains these four projections and the exact
post-Seal WAL overlay.

## Version relationship

The durable versions remain independent:

| Surface | Version in this RFC | Meaning |
| --- | --- | --- |
| Seal key namespace | `seal/v1` | canonical object-key spelling |
| Seal envelope | 2 | Seal body codec |
| `SealFormat` | V2 | four-tree semantics and comparators |
| WAL key namespace | `wal/v1` | canonical object-key spelling |
| WAL envelope | 1 | unchanged current fact codec |
| table key namespace | `table/v1` | canonical SST object spelling |
| SST object | 1 | fixed identity header plus rows through EOF |
| Directory row codec | 1 | previous-key path-prefix rows |
| Ledger row codec | 1 | fixed UID plus value-or-delete rows |

Seal envelope version 2 accepts only `SealFormat::V2`. The V2 Seal decoder
does not decode envelope version 1 as an empty approximation, and the V1
decoder does not accept a V2 body.

`SealFormat::V2` has durable numeric tag 2. The V2 private Postcard wire uses
the Seal and manifest field order shown in this RFC. Manifest `KeyBound` tags
are `Minimum = 1`, `Key = 2`, and `Maximum = 3`; zero is reserved. Domain
enums do not derive their durable representation implicitly: private wire
types translate every durable tag explicitly, and golden vectors anchor the
complete bytes.

The table key namespace version does not advance merely because a later SST
object version is introduced. Object spelling and object contents are
distinct contracts.

RFC 0002's CRC-32C envelope remains the Seal and WAL framing decision. It is
not extended to SSTs and does not transitively prove SST contents.

## Table identity and spelling

SSTs are immutable content objects and use the architecture's fresh identity:

```rust
struct AttemptId {
    owner_claim: SealGeneration,
    local_counter: u64,
}

struct FreshIdentity {
    birth_generation: SealGeneration,
    attempt: AttemptId,
    ordinal: u32,
}

struct TableObjectId {
    fresh: FreshIdentity,
    store: StoreKind,
}
```

The key shape is:

```text
partition/<partition>/table/v1/<store>/<birth>/<owner>-<attempt>/<ordinal>
```

`birth`, `owner`, and `attempt` are zero-padded 20-digit decimal values.
`ordinal` is a zero-padded 10-digit decimal `u32`. `birth` and `owner` are
nonzero generations; attempt counter and ordinal may be zero. Store spelling
is the lowercase canonical name above. Parsers reject any alternate width,
sign, separator, case, extra segment, overflow, zero generation, or key/body
identity mismatch.

Example shape, with the UUID abbreviated only here:

```text
partition/<uuid>/table/v1/directory/
00000000000000000002/00000000000000000001-00000000000000000000/0000000000
```

Real golden vectors use a complete canonical UUID and one line.

`birth_generation` is the candidate Seal generation that may first select the
table. `owner_claim` identifies the directly authored claim under which the
attempt began. `local_counter` distinguishes attempts under that claim, and
`ordinal` distinguishes outputs within one attempt. A valid fresh identity
has `owner_claim < birth_generation`; all increments and comparisons are
checked.

A retry freezes and create-or-verifies the same bytes at the same identity, or
starts a new attempt with fresh identities. It never adopts an arbitrary
orphan found by LIST or content hash.

## Manifest vocabulary

The real manifest is:

```rust
struct TreeVersion {
    ranges: BoundedNonEmptyVec<RangeVersion>,
}

struct RangeVersion {
    start: KeyBound,
    end: KeyBound,
    runs: BoundedVec<SortedRun>, // newest to oldest
}

enum KeyBound {
    Minimum,
    Key(Box<[u8]>),
    Maximum,
}

struct SortedRun {
    tables: BoundedNonEmptyVec<TableRef>,
}

struct TableRef {
    object: TableObjectId,
    object_bytes: NonZeroU64,
}
```

Ranges are half-open under the store comparator. `Minimum` is below every key
and `Maximum` is above every key. In `SealFormat::V2`, every tree has exactly
one range with `(Minimum, Maximum)` bounds. `Key` remains in the durable shape
so a later Seal format can define multiple ranges; V2 rejects it in a range
boundary.

The canonical empty tree has one full-keyspace range and no runs. An empty run
or empty table is illegal.

The Seal directly bounds and validates every manifest collection without
fetching children:

```text
exactly one full range
runs newest to oldest by position only
every run non-empty
every table object has the enclosing StoreKind
every table birth_generation <= the enclosing Seal generation
every TableRef.object_bytes is nonzero and <= SST_OBJECT_BYTES_MAX
every object identity occurs at most once in the complete Seal
all counts and encoded bytes remain below their named bounds
Tally and Annals equal canonical empty
```

Table key bounds and entry counts are deliberately not duplicated in the
Seal. A direct claimant derives them while performing the full scan it already
must do.

The loaded manifest additionally validates:

```text
every table is non-empty
every table's exact derived key range lies in its owning range
tables inside one run are ordered and key-disjoint
the table header identity and codec match its key, TableRef, and owning tree
all decoded counts and byte sums remain bounded
```

Only then may raw `TreeVersion` become `LoadedTreeVersion`.

## Initial bounds

Every encoder enforces the same bound as its decoder. Bounds cover complete
encoded regions, not only logical payloads.

| Bound | Value | Covers |
| --- | ---: | --- |
| `SEAL_ENCODED_BYTES_MAX` | 1 MiB | complete V2 Seal frame |
| `TREE_RANGES_MAX_V2` | 1 | the one full range |
| `TREE_RUNS_MAX` | 16 | hard runs per tree |
| `RUN_TABLES_MAX` | 4096 | tables in one run, also constrained by Seal bytes |
| `SST_OBJECT_BYTES_MAX` | 128 MiB | complete table object |
| `DIRECTORY_KEY_BYTES_MAX` | 512 bytes | canonical stream path |
| `STREAM_RECORD_BYTES_MAX` | 1 KiB | one frameless Ledger value |
| `PARTITION_PATH_OCCUPANCIES_MAX_V2` | 10,000,000 | lifetime Directory rows and allocated UIDs |
| `PARTITION_RESIDENT_LOGICAL_BYTES_MAX_V2` | 16 GiB | merged Directory and Ledger row accounting |
| `PARTITION_BOOTSTRAP_OBJECTS_MAX_V2` | 1024 | selected Directory and Ledger `TableRef`s |
| `PARTITION_BOOTSTRAP_BYTES_MAX_V2` | 32 GiB | sum of selected Directory and Ledger object lengths |
| `WAL_SUFFIX_COORDINATES_MAX_V2` | 1024 | inclusive coordinate span from the Seal cut through the claimant FENCE |

The 1 MiB Seal bound is also the hard aggregate manifest bound; local element
bounds never authorize an oversized Seal. A builder stops before adding an
element that would exceed any count, byte, or integer-representation limit.

Byte bounds run before Postcard parse. Every private wire sequence and byte
string uses a bounded visitor: an over-limit declared length is rejected
before allocation, and an indefinite or dishonest source is stopped before
materializing element `MAX + 1`. Wire values become domain values only after
all local and relational bounds pass.

The initial writer target is 64 MiB per SST, below the 128 MiB acceptance
bound. The target is policy and may change after measurement without changing
the decoder contract.

`SST_OBJECT_BYTES_MAX` remains below the object adapter's PUT bound. The
engine carries constant assertions for bounds that cross crate ownership.
Combined with RFC 0002's existing 4 MiB per-coordinate and 4096-fact per-RUN
bounds, the suffix-span bound derives maxima of 4 GiB encoded bytes and
4,194,304 facts. It needs no redundant byte or fact counter. RUN and FENCE
objects both consume one coordinate; FENCEs contain no facts.

Resident logical bytes use a representation-independent worst-row account:

```text
Directory row = 13 + complete path bytes
Ledger Value  = 11 + canonical StreamRecord bytes
Ledger Delete = 9 bytes before newest-wins merge; zero resident bytes after it
```

At ten million live streams with every path and record at its maximum, this is
`10,000,000 * (525 + 1,035) = 15,600,000,000` bytes, approximately 14.53 GiB.
The 16 GiB logical bound therefore covers the named scale without relying on
prefix compression. Prefix compression reduces transfer bytes, not this
admission proof.

An implementation also has an explicit `ResidentLoadBudget` for actual
physical bytes, including allocator, index, and bootstrap-staging overhead. A
worker is eligible to claim a V2 production partition only if its advertised
class can load the full 16 GiB logical state under its chosen representation;
placement checks that class before claim. A smaller development worker may
load a smaller manifest, but may not be the only recovery target for a
partition allowed to admit toward the production limit. The measurement plan
must establish the physical budget on a named reference worker before the
ten-million-stream viability goal is considered demonstrated.

## Storage trust and integrity

The initial deployment contract trusts the selected S3-compatible backend and
transport to return exactly the bytes of a successfully completed immutable
object. Concretely, StromDB relies on:

- atomic completed object creation rather than torn visibility;
- strong read-after-create for the created key;
- object bytes remaining immutable while the key exists;
- TLS and the provider/SDK's transport and at-rest integrity checks; and
- Courant-owned namespaces not being overwritten by another actor.

Within that trust boundary, a second application checksum over the same SST
bytes does not participate in publication authority and is not essential for
correctness. StromDB therefore adds no SST CRC, digest, footer checksum, block
checksum, or checksum composition in V1.

StromDB itself detects:

- absence of a selected object;
- a body shorter or longer than the exact `TableRef.object_bytes`;
- a body above the hard object bound;
- object-key, partition, store, or table-identity disagreement;
- bad magic, object kind, version, or row codec;
- a row truncated in a fixed-width or declared-length field;
- malformed or noncanonical value encoding;
- unknown tags, zero identities, unsorted keys, or duplicate keys;
- table/run/range structural contradictions; and
- forest and WAL-fold logical contradictions.

This does not promise independent detection of a same-length mutation that
still decodes as a different valid table, malicious storage that rewrites a
coherent object, or a coherent writer bug. Those are outside the V1 storage
threat model. If operations, another backend, or the Annals remote-read path
requires protection against them, the smallest next step is an explicit
whole-object digest in a later `TableRef` and Seal format. That decision does
not justify a footer/block hierarchy today.

Integrity is also distinct from authority. The existing CRC on a Seal or WAL
frame detects accidental frame damage; only the permanent Seal protocol and a
`Direct` result grant authority.

## Object-store read seam

Directory and Ledger V1 need one read operation:

```rust
async fn read(
    key: &ObjectKey,
    bytes_max: ByteBound,
) -> Result<Option<RawObject>, StoreError>;
```

The engine passes `TableRef.object_bytes` after proving it is within
`SST_OBJECT_BYTES_MAX`, then requires the returned body length to equal that
exact value.

The adapter may reject immediately when reported object metadata exceeds the
bound, but metadata is only an optimization. It must also enforce the bound
while consuming the response body and stop after observing one byte beyond
`bytes_max`; it must not call an unbounded collect operation merely because
`Content-Length` claimed a smaller value. Absence remains distinct from an
empty object and from a transport failure.

The current `read_range(key, range, expected_crc)` and
`VerifiedRangeBytes` seam is removed from the required V1 adapter contract. It
is not a durable format constraint. A future Annals RFC may introduce a
range-read capability whose integrity mechanism follows its actual object
format and backend requirements.

Provider checksum validation may be enabled inside the adapter. Provider
headers, ETags, and checksum algorithms are observations, not fields in the
SST wire contract.

## SST object layout

An SST is one fixed header followed by one or more rows through exact object
end:

```text
offset 0
+-----------------------------+
| fixed SST header            |
+-----------------------------+
| row 0                       |
+-----------------------------+
| row 1                       |
+-----------------------------+
| ...                         |
+-----------------------------+  exact TableRef.object_bytes
```

There is no footer, block wrapper, index, filter, checksum trailer, padding,
explicit row count, or end marker. EOF is legal only immediately after a
complete row. EOF inside a fixed field, declared value, or path suffix is a
typed malformed-table error. A header with no rows is invalid; empty logical
trees use the canonical empty manifest instead of empty tables.

The fixed 52-byte header is:

```text
magic "STRM"                         4 bytes
object kind = SST                    u8, tag 3
SST version = 1                      u8
partition                            16 canonical bytes
birth_generation                     u64 big-endian
owner_claim                          u64 big-endian
attempt local_counter                u64 big-endian
ordinal                              u32 big-endian
store                                u8
row codec                            u8
```

The identity fields and `store` are exactly `TableObjectId`; they are not a
second independent identity. The decoder compares them with the durable
object key and `TableRef` before decoding a row. `row codec` tags are
`DirectoryV1 = 1` and `LedgerV1 = 2`; zero stays reserved. Under
`SealFormat::V2`, only the matching codec is legal for each non-empty store.

The fixed header is manually encoded. Numeric values never inherit host
endianness, and durable tags never derive from Rust enum layout. Golden bytes
anchor the complete header and rows.

## Directory row codec V1

Directory rows are prefix-compressed against the immediately previous key:

```text
shared bytes with previous path       u16 big-endian
path suffix bytes                     u16 big-endian
entry tag                             u8: 1 = Live, 2 = Tombstone
StreamUid                             u64 big-endian
path suffix                           declared bytes
```

The first row has `shared = 0` and carries its complete key. Every later row
uses the complete longest common prefix with the preceding materialized key.
The decoder recomputes that prefix and rejects a shorter noncanonical spelling.

Before yielding a row, decode validates:

```text
complete fixed prefix and suffix are present
shared <= previous key length
materialized key length is nonzero and <= DIRECTORY_KEY_BYTES_MAX
materialized bytes parse as one canonical DirectoryKey
key is strictly greater than the previous key
entry tag is Live or Tombstone
StreamUid is nonzero
row count uses checked arithmetic
```

Both entry tags are logical values. There is no Directory physical-delete
tag. Prefixing against the previous key is intentionally sequential: remote
seeking into this table is not a V1 operation. A table boundary resets the
previous key.

## Ledger row codec V1

Ledger uses fixed keys and a value-or-delete row:

```text
StreamUid                             u64 big-endian
cell tag                              u8: 1 = Value, 2 = Delete

if Value:
    value bytes                       u16 big-endian
    StreamRecord                      declared Postcard bytes

if Delete:
    no length and no value bytes
```

The value length is nonzero and at most `STREAM_RECORD_BYTES_MAX`. The decoder
consumes exactly that slice as one `StreamRecord`, rejects trailing value
bytes, re-encodes the result, and requires byte-for-byte equality with the
input slice.

Before yielding a row, decode validates:

```text
complete UID and tag are present
UID is nonzero and strictly greater than the previous UID
cell tag is Value or Delete
Value length and complete bytes are present and bounded
Value is one valid canonical StreamRecord
Delete consumes no length or value bytes
row count uses checked arithmetic
```

There is no LSM sequence number, storage timestamp, per-row checksum, offset
array, restart interval, or repeated UID inside `StreamRecord`.

## Logical tree value

For one full range, a tree's logical value is newest-run-wins:

```text
for key K:
    inspect runs from newest to oldest
    the first value or Ledger Delete is authoritative
    no row means absence
```

One run contains at most one row per key. Tables inside the run are ordered
and key-disjoint, so at most one table in that run can contain a key.

Directory has no delete representation, so its result is either absent,
`Live`, or `Tombstone`. Ledger `Delete` resolves to logical absence after
hiding every older value.

An implementation may recover by k-way merge, by scanning oldest to newest
and overwriting resident state, or by another bounded algorithm. It must
produce the same value and use finite fan-out.

## Bootstrap and reads

Only a direct claimant loads admission-resident state. For every Directory
and Ledger table it performs:

```text
validate TableRef.object_bytes against the hard and resident budgets
-> bounded whole-object GET
-> require actual bytes == TableRef.object_bytes
-> validate the fixed header against key, partition, store, and TableRef
-> sequentially decode rows to exact EOF
-> derive exact row count and minimum/maximum key
-> validate table order, run disjointness, and range ownership
```

Before issuing table GETs, the claimant sums with checked arithmetic every
selected Directory and Ledger `TableRef`. The count and encoded-byte sums must
fit `PARTITION_BOOTSTRAP_OBJECTS_MAX_V2` and
`PARTITION_BOOTSTRAP_BYTES_MAX_V2`, then the worker's physical
`ResidentLoadBudget`. During decode it also checks running row and resident
logical-byte budgets before each allocation or insertion. The absence of row
counts in the manifest never authorizes unbounded materialization.

The simplest conforming loader reads and decodes one table at a time. Bounded
parallelism may be added as policy, but cancellation must stop scheduling new
work and no implementation may multiply the per-object bound by unbounded
fan-out.

Bootstrap decodes into an abortable, unpublished builder. It validates the
complete run/table structure, merges both logical stores, and proves the
cross-store invariants before constructing one `LoadedForest`. A malformed
last row or last table therefore cannot expose the valid prefix as resident
state.

It then discovers the first-hole FENCE and replays the exact WAL suffix through
the same strict fold. Before issuing per-coordinate GETs, checked subtraction
proves that the inclusive span from the Seal cut through that FENCE fits
`WAL_SUFFIX_COORDINATES_MAX_V2`; a huge or wrapped coordinate never drives a
huge loop. Each RUN or FENCE still passes RFC 0002's existing frame and fact
bounds before fold. Readiness requires the resulting four-store
`LoadedForest`; absence, malformed bytes, an
over-bound source or suffix, a capacity refusal, or a logical contradiction
cannot be treated as an empty tree or an older convenient state.

A physical-capacity refusal leaves the partition Unready but does not relabel
otherwise valid durable bytes as corruption. In production it means placement
selected an ineligible worker or the implementation's measured representation
budget was wrong; admitted churn cannot exceed the fixed logical capacity.
Placement may retry only on an eligible worker. Recovery never skips tables,
WAL coordinates, or falls back to an older Seal.

Runtime Directory and Ledger reads are resident. The durable RFC requires:

- exact Directory lookup;
- ordered Directory prefix iteration;
- exact UID Ledger lookup; and
- immutable published views.

It does not select `BTreeMap`, packed sorted vectors, a hash accelerator, a
dense vector, or a segmented vector as the resident representation. V1 does
require the complete logical Directory and Ledger state to be answerable from
RAM; local files and NVMe belong to the deferred two-tier design.

## Flush

For checkpoint prefix `(P, W]`, strict fold computes final absolute state for
each touched key at exactly cut `W`. A store emits a row only when that key's
logical value differs from its value at source cut `P`:

```text
Directory: final Live or Tombstone for each changed path
Ledger:    final Value different from source -> Value
           final absence with a source value -> Delete
           final state equal to source -> no row
```

In particular, a stream created and hard-deleted wholly inside `(P, W]`
produces a permanent Directory tombstone but no Ledger row. Strict fold rejects
duplicate or no-op lifecycle facts; flush does not need special idempotency
semantics.

The builder independently sorts and deduplicates each store, encodes bounded
tables, and groups the tables into at most one new newest run per touched
tree. Directory prefix state resets for each new table. A table is frozen
before its `TableRef.object_bytes` is constructed. An untouched tree is copied
exactly. An empty effect set does not create an empty run or table.

All output identities use the candidate generation and one named attempt.
Every child is create-or-verified durable before the candidate Seal is
encoded. Only conditional creation of the complete Seal publishes the
Directory and Ledger effects together. If any child preparation fails, no
partial logical state exists; already-written children are unreachable
orphans.

The checkpoint builder must not observe state above `W`. Later accepted WAL
facts remain only in the post-Seal suffix until a later checkpoint.

## Initial base-plus-deltas policy

The durable manifest contains only ordered runs; it has no level, base, or
bottom tag. Initial maintenance uses the following operational discipline:

```text
runs = [newest delta, ..., oldest delta, materialized base]
```

Genesis is an implicit empty base. The first flush from genesis is a complete
base for the state at that cut. Later checkpoint flushes prepend deltas.

The hard manifest limit is 16 runs per tree. Eight runs is the initial
maintenance high-water mark: below the hard limit, the scheduler may publish
an opportunistic same-cut full compaction. Checkpoint progress never depends
on that maintenance succeeding.

A normal advancing checkpoint may prepend a delta only when the candidate
remains within the run, aggregate bootstrap-object, and aggregate
bootstrap-byte bounds. If adding a delta would cross any of those bounds, the
advancing checkpoint instead materializes that tree's complete logical state
at its selected cut `W` as one new base run. It folds exactly the same selected
WAL prefix as an ordinary checkpoint; it is an `advance`, not a new
correctness transition:

```text
full-base checkpoint
    = merge every source run
    + strict-fold source WAL prefix (P, W]
    -> one replacement run at logical cut W
```

Directory and Ledger decide independently whether to emit a delta or full
base, and the one candidate Seal publishes both decisions atomically. Thus a
seventeenth run is not a reason to reject checkpointing. A complete base at
the partition's maximum logical capacity fits the aggregate bootstrap bounds
by construction.

Both an advancing full-base checkpoint and a same-cut full compaction emit a
complete replacement tree using these rules:

- newer input wins for duplicate keys;
- every Directory key is emitted as its final logical value;
- final Ledger values are emitted;
- final Ledger deletes are omitted because the selected interval reaches the
  oldest run; and
- output tables are newly identified immutable objects.

If the selected Ledger state is empty, either operation publishes the
canonical empty tree instead of an empty replacement run. Directory cannot
return to empty after its first successful create because path occupancy is
permanent.

A same-cut maintenance Seal carries the unchanged logical cut and other three
trees. It changes physical view identity through its new generation. An
advancing full-base Seal carries the selected greater cut and releases the
covered replay suffix exactly like every other checkpoint.

Checkpoint and maintenance candidates share one local publication lane. At or
above the eight-run high-water mark, or while mutation admission is
backpressured, advancing checkpoint work has priority and new same-cut work is
not started. A candidate already tied to an older source is abandoned if
another successor wins; it is never rebased.

Adjacent-delta merging is legal under the same precedence rules but is not
required initially. The scheduler, thresholds, table reuse, and concurrency
are policy rather than durable format semantics.

Ledger UID creation is append-majority, not perfectly disjoint: one flush can
contain an old UID lifecycle update and a high-UID creation suffix. Separating
those bands into distinct tables and carrying disjoint suffix tables through
compaction is deferred until measurement justifies the extra planner.

## Checkpoint lag and admission backpressure

The post-Seal WAL suffix is bounded durable state, not an unbounded escape
valve for failed checkpoints. Its inclusive coordinate span from the Seal cut
must remain within `WAL_SUFFIX_COORDINATES_MAX_V2`; RFC 0002's per-coordinate
bounds then bound total encoded bytes and facts.

Before admitting a mutation group to the next WAL RUN, the Ready writer checks
the projected suffix including that RUN and reserves one additional coordinate
for a future claimant's first-hole FENCE. The proposed RUN is already limited
to 4096 facts and 4 MiB by RFC 0002. The final recovery FENCE consumes the
reserved coordinate and contains no facts.

If any projection does not fit:

- the mutation group does not enter `AdmittedState`, `PendingRun`, or a WAL
  create;
- no externally visible UID is consumed and no success is acknowledged;
- the serving layer returns a retryable overload response;
- immutable reads from the current `PublishedView` remain available; and
- the scheduler prioritizes an advancing full-base checkpoint through the
  greatest currently durable coordinate.

Admission resumes only after a successful advancing Seal moves the replay cut
far enough to restore the recovery reserve. The gate applies to every mutation,
not only creation. Repeated child or Seal failures can therefore make the
partition read-only, but cannot grow its WAL suffix, replay work, or
admission-to-durability memory without bound.

Recovery enforces the same span limit through its newly placed FENCE. A
history that already leaves no room for that FENCE remains Unready rather than
silently truncating replay. This is a bounded liveness failure: stale claims
and permanent FENCEs can consume the suffix budget across repeated crashes,
and recovery then requires an operator-directed repair or a later recovery
RFC. Normal Ready admission always leaves room for one takeover.

## Failure and publication rules

SST objects carry no authority until selected by a Seal. Their writer may use
content-object create-or-verify at one fresh identity. It may not overwrite a
different occupant, select a partially observed object, or manufacture success
from LIST.

Preparation order between touched stores is not a transaction protocol. The
required order is only:

```text
freeze each bounded candidate exactly once
-> make every selected child durable or abandon the candidate
-> encode one complete Seal from source-carried and fresh child identities
-> conditionally create the exact successor Seal
```

An ambiguous child result is reconciled by a bounded read and exact byte
comparison with the frozen candidate. An ambiguous Seal result follows the
existing Seal protocol and never causes a blind resend. On fencing or poison,
readiness is revoked and a fresh bootstrap decides from durable evidence.

Cancellation before the Seal create begins abandons the candidate and leaves
only unreachable children. Once conditional Seal creation begins, cancellation
cannot be interpreted as non-publication: the task must retain and reconcile
the exact frozen request, or revoke readiness and let bootstrap decide. This is
the existing publication rule applied to a larger checkpoint, not a special
full-base state.

SST GC is not authorized by this RFC. Orphans and superseded tables may leak.

## Tests

### Golden formats

- V2 genesis Seal with four canonical empty trees.
- V2 Seal with one Directory run and one Ledger run.
- Canonical table-object key for every `StoreKind`.
- Complete Directory SST with one row and with multiple prefix-sharing rows.
- Complete Ledger SST with `Value` and `Delete` rows.
- WAL V1 vectors proving the `LedgerKey` to `DirectoryKey` source rename did
  not change bytes.

Golden vectors are independent byte constants, not encode-then-decode tests.

### Decode gates and malformed input

- Over-bound Seal, manifest collection, object, key, value, or resident row
  budget.
- Aggregate Directory-plus-Ledger bootstrap object count and encoded bytes at
  exactly the limits and one beyond each limit.
- Actual object shorter or longer than `TableRef.object_bytes`, including a
  response whose metadata falsely claims an in-bound length.
- Bad magic, object kind, version, `StoreKind`, row codec, or identity.
- Future table birth, owner claim not older than birth, or duplicate object
  identity.
- Header-only table, EOF inside every fixed and declared field, and bytes that
  cannot begin a legal next row.
- Directory non-longest prefix, prefix beyond previous key, unknown tag,
  malformed path, zero UID, duplicate path, or unsorted path.
- Ledger zero, duplicate, or unsorted UID; unknown tag; zero, oversized,
  truncated, malformed, noncanonical, or trailing value bytes.
- Incorrect derived table ordering, overlap, or range ownership.
- A failure in the final row or final table abandons the staged load and
  exposes no partial `LoadedForest`.

Every failure is typed and constructs no partial durable domain value. V1
does not include a test claiming that every arbitrary same-length bit flip is
detected, because that is not its integrity contract.

### Properties and models

- Directory row encode/decode preserves arbitrary sorted canonical maps and
  always emits the longest previous-key prefix.
- Ledger row encode/decode preserves arbitrary sorted UID cell maps.
- Arbitrary legal run stacks equal a simple newest-wins map model.
- Same-cut full compaction and advancing full-base checkpoints preserve their
  respective transition equations.
- Directory compaction never decreases entry count or changes a UID.
- Ledger deletes never resurrect an older value.
- Dense UID create, close, and delete histories preserve every cross-store
  invariant.
- At 9,999,999 lifetime paths one final create succeeds; the next new path is
  rejected before a UID, fact, or WAL object, and deleting any prior stream
  does not restore capacity.
- The worst-row capacity formula remains below 16 GiB at ten million and
  exceeds it if any configured field bound is raised incompatibly.
- In the no-forks slice, explicit delete produces a permanent Directory
  tombstone and logical Ledger absence. A model extension covers retained
  soft deletion with an inbound reference and cascading reclamation when the
  final reference disappears before forks ship.
- Checkpoint output equals strict fold from the exact source through the exact
  selected WAL prefix.
- A delta at the sixteenth run or aggregate bootstrap budget selects an
  advancing full-base plan, emits at most one replacement run per rewritten
  tree, and advances the WAL cut.
- Maintenance output equals its exact source logical state.
- Every selected child in generated candidates is source-carried or has the
  candidate generation as its birth generation.
- Prefix candidate scans plus the protocol glob matcher equal a full-scan glob
  model, including the exact literal path when terminal `**` matches zero
  segments.

### Recovery and publication

- Reopen from non-empty Directory and Ledger SSTs and reconstruct the same
  resident forest.
- Replay a WAL suffix over the loaded base and compare with uninterrupted
  strict fold.
- Crash or failure at every child-preparation boundary leaves either the old
  Seal authoritative or the complete new Seal authoritative, never a mixed
  forest.
- Missing or malformed current children prevent Ready.
- A physical, object-count, row-count, or decoded-byte load budget is exceeded
  before Ready without exposing partial resident state.
- Same-cut full compaction changes physical identity without changing logical
  state.
- Repeated checkpoint child and Seal failures fill the allowed WAL suffix;
  the next mutation receives retryable overload without a WAL create, while
  reads remain available. A later successful full-base checkpoint restores
  admission.
- RUNs and FENCEs both consume the coordinate span, and Ready admission always
  leaves one FENCE of takeover reserve.
- Recovery whose inclusive first-hole FENCE exceeds the suffix bound remains
  Unready without replaying a convenient prefix.
- Crash or cancellation before and after the conditional Seal-create boundary
  follows the ordinary ambiguous-publication reconciliation rule.

Adapter contract tests separately prove bounded whole reads, including a
dishonest reported size, exact byte comparison for create-or-verify,
conditional-create observations, absence, and transport-error classification.

## Initial measurement plan

Before declaring the ten-million-stream goal demonstrated or treating the
writer target as a default beyond this slice, run the complete matrix on a
named production reference worker and the intended S3 deployment:

```text
partition scale:
    1 million and 10 million lifetime paths

live / tombstone ratio:
    100/0, 50/50, 10/90, 1/99

Directory path shapes:
    short flat benchmark paths
    hierarchical paths with shared segments
    adversarial 512-byte paths with little shared prefix

Ledger values:
    minimum, representative, and 1 KiB maximum records

physical histories:
    1, 8, and 16 runs
    empty WAL suffix and suffix at the replay high-water mark

table target:
    16 MiB, 64 MiB, and 128 MiB
```

For each relevant corner, record:

- logical and encoded bytes per row, prefix-compression ratio, table count,
  object count, and transferred bytes;
- cold bootstrap GET count, transfer and decode throughput, replay time, total
  time to Ready, and failures at every configured budget;
- actual steady-state and peak bootstrap RSS, including allocator, index,
  merge, and staged-publication overhead;
- delta-checkpoint and full-base elapsed time, CPU, peak memory, bytes
  read/written, orphan bytes after injected failure, and time for the WAL cut
  to advance;
- group-commit admission throughput and p50/p99 while idle, during delta
  checkpointing, and during a ten-million-row full-base checkpoint; and
- overload onset at the suffix bound, read latency while mutation admission is
  stopped, and time to resume after checkpoint recovery.

The result must name the worker's CPU, memory, resident representation,
adapter concurrency, backend, and measured physical `ResidentLoadBudget`.
The V2 production placement class must cover the measured ten-million-row
peak with explicit operational headroom. Until that run also records and meets
a named bootstrap-to-Ready objective, architecture requirement 9 is bounded
by design but not claimed as performance-proven.

The measurements answer whether the next useful optimization is a different
table target, streaming decode directly from the response, general
compression, a packed resident representation, or a local NVMe tier. They do
not pre-authorize blocks, filters, or range reads. Annals supplies a separate
workload study before choosing its physical read format.

## Alternatives not selected for V1

**Keep path and record in one Ledger tree.** This retains wide path keys in
the larger object store, makes permanent occupancy dictate record retention,
and couples prefix-scan encoding to UID lifecycle access. The single Seal
already provides atomic publication across two trees, so the split does not
need a second transaction protocol.

**Build a dedicated fifth glob index now.** Whole-segment glob syntax already
gives resident Directory a lexical descendant prefix and at most one exact
path candidate. A fifth tree adds write and bootstrap work before evidence
shows that candidate filtering is a bottleneck. A segment-inverted index
remains a compatible later forest member.

**Put a whole-object checksum or digest in `TableRef`.** This would detect
otherwise-valid same-length mutation beneath the selected identity. The V1
S3 trust contract does not require that extra detector. If that assumption
changes, one digest is the first design to evaluate; it does not require
blocks or a footer.

**Authenticate a footer and every data block.** Directory and Ledger issue
whole-object bootstrap reads and no remote point reads. A Seal-to-footer-to-
block checksum graph, child spans, CRC composition, and verified-range
capabilities solve an absent access path while multiplying states and decode
gates.

**Keep an optional filter or index section for Annals.** No current store uses
it, and Annals has not yet fixed its key, filter target, range-read pattern, or
payload relationship. V1 has no empty extension slots. The first remote-read
RFC may define an SST V2 or a store-specific content format from measured
needs.

**Use restart points for Directory prefix encoding.** Restart points permit
entry seeking from inside a table. V1 always scans from the beginning, so
prefixing against the previous row is smaller and simpler.

**Start with generic leveled compaction.** One base plus bounded deltas covers
the create-heavy resident trees. Multiple ranges, leveling, and sophisticated
scheduling add durable and operational states needed by Annals, not by this
slice.

**Remove the existing Seal and WAL CRCs in this RFC.** Those small-object
envelopes are an already accepted RFC 0002 decision and do not create the SST
hierarchy being removed here. Reconsidering them would be independent cleanup,
not a prerequisite for this slice.

## Implementation slices

1. Rename and split storage vocabulary into Directory and UID-keyed Ledger;
   preserve WAL V1 golden bytes.
2. Add dense UID fold invariants, lifetime-path admission capacity, and the
   pure two-map reference model.
3. Add Seal envelope V2, `SealFormat::V2`, four fields, real empty
   `TreeVersion`, table identity spelling, and length-only `TableRef`.
4. Make whole-object reads enforce the actual streamed-byte bound; remove the
   expected-CRC range-read requirement from this slice.
5. Add the fixed SST header and Directory sequential row writer/reader.
6. Add the Ledger sequential row writer/reader.
7. Add aggregate source bounds, staged whole-table bootstrap, logical merge,
   cross-store checks, physical-budget gates, and atomic `LoadedForest`
   construction.
8. Add checkpoint delta construction and complete candidate Seal publication.
9. Add advancing full-base checkpoints, optional same-cut compaction, and the
   single priority publication lane.
10. Add WAL-suffix span accounting, recovery-FENCE reserve, and retryable
    mutation backpressure.
11. Add fault, reopen, property, model, capacity, and ten-million-scale
    measurements.

Each slice keeps workspace metadata and lints inherited, crosses the same
production/test seam, and passes `just ci` before commit.

### Forks and soft deletion

- parent UID, fork boundary, and lineage traversal;
- inbound fork reference counts and inherited-data pins in Tally;
- soft-deleted and expired-but-retained Ledger values;

- Annals and payload reachability proof before physical collection.

That RFC must preserve the rule
`(deleted or expired) && inbound_fork_refs == 0` for full reclamation. It may
change the no-forks cross-store invariant explicitly, but may not make close a
deletion condition or make path reuse depend on asynchronous garbage
collection.

### Subscription execution

- backfill job lifecycle and response semantics;
- scan batching, cancellation, and resumable progress;
- link rows and fanout;
- a segment-inverted namespace index if ordered Directory scans prove
  insufficient.

### Advanced LSM policy

- multiple key ranges and range boundary changes;
- adaptive size-tiering or leveling;
- adjacent-delta selection policy;
- metadata-only concatenation of disjoint UID tables;
- table reuse, subcompactions, distributed compaction, and scheduling weights.

### SST garbage collection

- reachability proof from a captured head;
- orphan and superseded-table age/watermark guard;
- compaction-state observation ordering;
- bounded LIST traversal and typed delete authorization.

Until that proof exists, safety permits SST leaks.

### Resident representation and tuning

- `BTreeMap`, packed vectors, hash accelerators, tries, and dense/segmented UID
  arrays;
- final table targets, bootstrap concurrency, delta budgets, and compaction
  thresholds.

V1 intentionally loads the complete logical Directory and Ledger into RAM so
group-commit admission never waits on S3. If lifetime occupancy later makes
that economically unattractive, the likely next design is a complete local
two-tier materialization: a bounded admission working set in RAM and colder
stream state in an NVMe-resident index rebuilt and validated from S3 before
Ready. An admission miss may then pay a measured local-device lookup, but never
an S3 request.

That design must name its RAM bound, cold classification, local lookup p99,
promotion and eviction rules, bootstrap construction, crash behavior, and
checkpoint interaction. NVMe remains disposable acceleration and does not
authorize path reuse or remove the ten-million lifetime-occupancy bound. All
of those choices are deferred; they may change without changing the durable
meaning specified here.
