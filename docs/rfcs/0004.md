# 0004: bootstrap, single-writer admission, and the persistent resident forest

This RFC makes the engine live. It joins the pieces that already exist — the
typed Seal and WAL stores, the checked SST codecs, and the pure `Forest`
fold — into one running partition: bootstrap from durable evidence, pure
admission, group commit through the WAL, and immutable published views.

It refines [`architecture.md`](../architecture.md) and RFC 0003, and
supersedes two of their provisional shapes:

- `PublishedView` carries no `DurableWalOverlay` in this slice. A view is one
  whole persistent `Forest` snapshot plus its Seal identity and replay cut.
- Genesis provisioning is engine-owned: `Engine::open` creates the
  canonical generation-1 Seal when the namespace is empty.

RFC 0003's `LoadedForest` type is not implemented. The existing `Forest` gains
one fallible constructor that proves the cross-store invariants; a separate
loaded-forest type would only duplicate it.

A companion implementation guide with module-level detail lives at
[`../plans/0004-bootstrap-writer-admission.md`](../plans/0004-bootstrap-writer-admission.md).
The guide is not normative; this RFC and the architecture are.

## Decision

One `Engine::open` entry point runs the explicit bootstrap phase machine,
then hands `Ready` state to one writer task:

```text
Engine::open
    -> provision genesis when the Seal namespace is empty
    -> bootstrap: DiscoverHead -> ReadHead -> PublishClaim
       -> LoadAdmissionBase -> PlaceFence -> Replay -> FinalRefresh -> Ready
    -> spawn the single writer task
    -> return { bounded command sender, view watch, writer join }
```

The writer is the sole owner of all mutable partition state. Its loop is the
architecture's hot path:

```text
receive a command
-> check the WAL suffix-span gate
-> admit through the one strict reducer
-> group-commit through zero-or-one in-flight WAL create
-> fold durable facts, publish one snapshot, release replies in order
```

Five choices fix this shape:

1. **Persistent resident maps.** `Forest` stores its Directory and Ledger rows
   in `imbl::OrdMap`. A snapshot is one O(1) structurally shared clone.
2. **One reducer everywhere.** Admission constructs a candidate fact and folds
   it into the admitted `Forest` with the same `strict_fold` that replay and
   recovery use. Only facts that returned `Applied` enter a WAL RUN.
3. **Views without an overlay.** Publication swaps one whole-forest snapshot.
   The base-plus-overlay split existed so a physical rewrite could install
   without repartitioning a resident suffix; a snapshot carries no physical
   range identity, so the concern disappears for the resident stores.
4. **Typed refusals, no barriers.** A duplicate or contradictory command gets
   an immediate typed refusal. Protocol idempotency and the
   `DurabilityBarrier` machinery arrive with the serving-layer RFC.
5. **No checkpoint yet.** The suffix gate sheds mutations with a retryable
   overload once the WAL budget is spent. A partition can therefore become
   read-only until the checkpoint RFC lands. Bounded read-only is acceptable;
   unbounded replay debt is not.

## Scope

This RFC specifies:

- the `imbl`-backed resident `Forest` and its merged-rows constructor;
- the read-only typed table store over the object-store adapter;
- engine-owned genesis provisioning and its evidence rules;
- the bootstrap phase machine, its witness types, and its failure policy;
- pure admission and the refusal vocabulary;
- the writer event loop, group commit, publication, replies, and exits;
- graceful shutdown; and
- the ingress bound and the WAL suffix-span admission gate.

It does not specify checkpoint flush, compaction, Seal advancement beyond the
bootstrap claim, WAL collection scheduling, protocol idempotency, forks, the
HTTP serving layer, Tally, or Annals.

## Persistent resident forest

`Forest` replaces its `BTreeMap` fields with `imbl::OrdMap` and derives
`Clone`. Structural sharing makes the clone O(1) and makes every published
view immutable for free.

`imbl` is a new workspace dependency. It is the maintained fork of `im`, it is
MPL-2.0 (already on the `deny.toml` allow list), and it is used only inside
the engine crate. No persistent type appears in a durable format.

Bootstrap constructs a `Forest` through one fallible constructor from the
merged Directory rows and Ledger values. The constructor proves the RFC 0003
cross-store invariants:

```text
every UID from 1 through the maximum has exactly one Directory row
Directory row count == maximum allocated StreamUid
every Live(uid) has exactly one Ledger value
every Ledger value has exactly one Live(uid)
every Tombstone(uid) has no Ledger value
```

A failed check constructs nothing. There is no partial forest.

## Published view without an overlay

```rust
struct PublishedView {
    seal: SealIdentity,      // the authored claim
    replay: WalReplayPoint,  // the logical cut carried by that claim
    forest: Forest,          // one persistent snapshot
}
```

The writer publishes through one `tokio::sync::watch` channel: fold the
durable facts, clone the forest, swap the view, then release replies.
Publication precedes reply, exactly as the architecture requires. Reads
resolve paths and records against a snapshot and never enter the command
queue.

## Genesis provisioning

The canonical genesis Seal is generation 1, `WalReplayPoint::Genesis`, and
empty trees. Its encoding is deterministic, so its bytes are canonical. When
`DiscoverHead` finds an empty namespace, `Engine::open` creates it:

| Evidence | Meaning | Action |
| --- | --- | --- |
| `Direct` | this call provisioned genesis | continue with head = genesis |
| `DurableMatch` | canonical genesis already exists | continue; genesis grants no ownership |
| `NotOurs` | foreign bytes at the genesis coordinate | typed contradiction |
| `Unresolved` | the create may still take effect | typed retryable exit; a new start is safe |

Every later phase treats absence as failure, never as an empty tree.

## Bootstrap

Bootstrap implements the architecture's `BootstrapPhase` machine directly.
The decisions this RFC adds:

- **Pure planners.** Source-bound accounting, run merging, the fence-candidate
  clamp, and the suffix-span check are pure functions, tested without I/O.
- **Witness types.** `AuthoredClaim` is constructible only from
  `CreateEvidence::Direct` on the exact claim Seal. `Ready` — the claim, the
  forest, the replay cut, and the next free batch — is constructible only by
  a bootstrap that passed every gate. A `Seal::claim_successor` helper builds
  the copied-manifest candidate so a malformed claim cannot compile.
- **No internal retries.** Every phase failure exits typed through one
  `BootstrapExit` with retryable, fenced, and contradiction classes. The
  caller may run `Engine::open` again; no phase loops inside an adapter.
- **Aggregate bounds first.** The claimant sums selected `TableRef` counts and
  bytes with checked arithmetic against the RFC 0003 bootstrap bounds before
  the first table GET, and proves the suffix span before the first WAL GET.

## Admission

Admission is pure and lives in its own module:

```rust
fn admit(
    admitted: &mut Forest,
    command: &StreamCommand,
) -> Result<OperationFact, AdmissionRefusal>;
```

`admit` constructs the candidate fact — allocating the create UID as
`path_count + 1`, resolving the path for close and delete — and folds it into
the admitted forest. `Applied` admits the fact; each `FoldContradiction` maps
one-to-one to a caller-facing refusal, and a refusal changes no state. This
satisfies RFC 0003's rule directly: normal admission constructs only facts
that return `Applied`, and admission, replay, and recovery share one reducer.

The only gate outside the fold is arithmetic: the projected suffix span
through the proposed RUN, plus one reserved FENCE coordinate for a future
claimant, must fit `WAL_SUFFIX_COORDINATES_MAX_V2`. A failed gate sheds with
a retryable overload before any UID, fact, or WAL create exists.

## Writer

The writer task owns the admitted forest, the durable forest, one bounded
`PendingRun` of accepted facts and reply waiters, and zero or one in-flight
frozen `EncodedWal`. WAL completion has priority over ingress. Evidence
handling follows the architecture's table: `Direct` folds, publishes, and
replies; `DurableMatch` is accepted only after exact byte comparison with the
frozen candidate; `NotOurs` exits `Fenced`; `Unresolved` reconciles with one
bounded exact GET or exits `Poisoned`.

A fold contradiction on the durable forest is an assert, not an error:
admission proved `Applied` for the same fact in the same process.

Graceful shutdown is the ingress channel closing. `Engine::shutdown`
drops the sender; the writer drains the already-queued commands, resolves the
active flight, publishes, replies, and exits `Shutdown`. There is no second
signal channel. Client cancellation only drops a reply waiter; it never
cancels a fact that may become durable.

## Bounds

One new named bound joins the existing ones in
`strom-storage-domain` `bounds.rs`:

| Bound | Value | Covers |
| --- | ---: | --- |
| `WRITER_INGRESS_COMMANDS_MAX` | 1024 | queued, not-yet-admitted commands |

`PendingRun` reuses `WAL_RUN_FACTS_MAX` and `WAL_ENCODED_BYTES_MAX`. The
admission gate reuses `WAL_SUFFIX_COORDINATES_MAX_V2`. A full queue or a full
`PendingRun` sheds with the same retryable overload as the suffix gate.

## Tests

The normative claims, detailed in the implementation guide:

- The table store proves exact-length agreement and treats absence, dishonest
  lengths, and failed decodes as contradictions.
- The run merge equals a newest-wins map model over arbitrary legal run
  stacks; every cross-store invariant violation is a typed construction
  failure with no partial forest.
- Bootstrap over the in-memory adapter covers genesis provisioning under
  every evidence outcome, reopen equivalence with an uninterrupted fold,
  every aggregate bound at the limit and one beyond, claim contention, and
  the final-refresh fence.
- Admission refusals are enumerated and leave state unchanged.
- Writer scenarios prove group commit under a slow flight, every evidence
  outcome, reply order equal to admission order, publication before reply,
  graceful drain, and overload shedding before any UID or WAL create exists.

## Deferred

- Checkpoint flush, full-base advancement, compaction, and the publication
  lane (RFC 0003 slices 8–10). The persistent forest gives the future
  checkpoint task a free consistent snapshot at its selected cut.
- Protocol idempotency, `DurabilityBarrier`, and deferred replies.
- The HTTP serving layer and read pagination; ordered Directory prefix scans
  stay internal until subscriptions need them.
- WAL RUN collection scheduling.
